# Instance powers are a `roles` set; the operator surface is `/admin`, gated on Superadmin

Instance-wide user powers were three orthogonal boolean flags on the `users` row — `is_admin` (account management), `can_create_worlds`, and `is_superadmin` — with the account-management flag surfaced in code and UI as "Admin" while the strictly more powerful operator was "Superadmin." That inversion was the confusion: the weaker tier held the plain word "Admin," and the account-management surface (`/admin`) mixed user management with the Superadmin-only Reindex. We remodel the two grantable flags (`is_admin`, `can_create_worlds`) into a single **`roles` set** on the user, rename the account-management surface to `/users`, and give the freed word **`/admin` to the operator's repair surface** (gated on Superadmin today). `is_superadmin` stays a separate flag.

This supersedes the storage-shape half of ADR-0040 (flags → set); the orthogonality decision 0040 records still holds — the set members are orthogonal, not a ladder.

## The decision

- **`roles` is a set, not a single value.** A user holds zero or more of `manage-users` (was `is_admin`) and `create-worlds` (was `can_create_worlds`). A single-valued enum can't represent "manages users _and_ may create Worlds" without making `manage-users` imply `create-worlds`, which contradicts the ADR-0037/0040 boundary that account management confers zero content powers. Stored as a zod-validated JSON text column (`roles`, default `'[]'`), mirroring `preferences` — always loaded whole with the user, never DB-queried.
- **Superadmin stays outside the set.** It is seeded, carries the content-ACL bypass, and holds hard invariants (last one irremovable; a `manage-users` holder cannot manage a Superadmin account). Keeping it a distinct flag keeps the `Superadmin ⊇ everything` implication and the last-superadmin invariant in one place, rather than denormalizing it into every Superadmin's `roles` array or special-casing set membership in the ACL.
- **Call sites read semantic helpers, not the raw array.** `AuthUser` exposes `canManageUsers` / `canCreateWorlds` (each `roles.includes(...) || isSuperadmin`) and `isSuperadmin`. The superadmin-implies-everything rule lives only in the helpers, so it can't drift; `roles` is pure storage.
- **`/admin` now means the operator surface.** The word "admin" moves off account management. Account management is `/users` (`UsersController @Controller('users')`, `ManageUsersGuard`), gated on `canManageUsers`. The Reindex repair tool moves to `/admin` (`AdminController @Controller('admin')`, `SuperadminGuard`), which is the operator's home for future repair tools. `is_superadmin` is unchanged — the surface is named for _where_ (admin/operator), the flag for _who_ (superadmin), a deliberate who/where split so an Instance Role could unlock `/admin` later without renaming anything.
- **`role` is deliberately scope-overloaded.** The codebase already uses `role` for collaboration standing (`owner`/`editor`/`viewer` on `world_members`/`entity_grants`). We accept "role" meaning both an account-wide power (Instance Role) and a per-resource standing (collaboration role), disambiguated by context, rather than coining a second word ("capability") — the operator asked for the mainstream "roles" mental model.
- **One write endpoint replaces the set.** `PATCH /users/:id/roles { roles }` sets the whole set (last-write-wins is acceptable on a small provisioned instance); any future role needs no new endpoint. The Superadmin toggle stays its own guarded route (`PATCH /users/:id/superadmin`). Migration adds `roles`, backfills from the two booleans in the same drizzle-kit migration, then drops them; `is_superadmin` untouched.

## Considered Options

- **Keep the three booleans, rename only the identifiers** — rejected. A pure rename leaves `is_admin` as a flag when the operator's mental model is "a set of roles," and every future instance power adds another boolean column plus another migration. ADR-0040 deferred the set model until a second capability appeared; the trigger here is different — naming legibility, not a new data point — but the remodel is cheap now and compounds later.
- **Fold Superadmin into the `roles` set** (`roles: ['superadmin', ...]`) — rejected. Superadmin sits outside the collaboration model, is seeded, and bears invariants the other two don't; as a set member, `Superadmin ⊇ Admin` forces either denormalized `manage-users` on every Superadmin row or set-membership special-casing throughout the ACL. A separate flag keeps the implication in one helper.
- **A `user_roles` join table** — rejected. The set is a tiny, closed, always-loaded-whole bag; a join table buys SQL queryability the app never uses and adds a read/write path. The JSON column matches the existing `preferences` precedent.
- **Name the set `capabilities` to avoid the `role` overload** — rejected by the operator in favour of the mainstream "roles" word, accepting the scope overload as the smaller cost.
- **Keep `/admin` meaning account management; put repair under `/superadmin`** — rejected. The operator wanted the powerful surface to hold the plain word "admin" (the "normal app" intuition), and naming it for the _surface_ rather than the _flag_ lets a future Instance Role unlock it without a rename.
