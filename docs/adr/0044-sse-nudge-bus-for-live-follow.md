# Live-follow via an SSE nudge bus, not state replication

A read-mode viewer (including an anonymous Public Link holder) sees another user's committed changes to an Entity or World **without refreshing**, over a single server→client **SSE** stream that carries *nudges* — "resource `X` is now at version `N`, refetch it" — never resource data. The refetch is the ordinary authorized `GET`, so the push channel replicates *no* state and shapes *no* per-viewer content — the single place resource data is projected through the access filter stays the `GET`. The bus itself runs only a cheap *reachability* check on emit (can this principal see `X` at all?), a boolean predicate on the existing access seam — not a second content-projection path. That reachability check is the price of leak-free fan-out and live eviction (below), not of nudge-vs-data: a data-push model would need the same boolean *plus* the projection this avoids. The same nudge primitive also cures the stale read-model problem that motivated this (the worlds list fetched once and mutated optimistically) — freshness and live-follow turn out to be one mechanism, not two.

This is deliberately **not** real-time co-editing. Content stays an opaque, format-tagged snapshot the domain never parses (ADR-0019); CRDT co-editing would breach that boundary and needs a *bidirectional* transport, so it arrives later alongside a WebSocket — the nudge bus is orthogonal to it and survives it, not throwaway bridge-work.

## Considered Options

- **Push the data, not a nudge** — rejected: broadcasting the new Content snapshot builds a second read path parallel to `GET`, with its own per-viewer access-control, diffing, and serialization surface to get wrong. A nudge carries no data, so the authorized refetch remains the single access-controlled read path.
- **WebSocket instead of SSE** — rejected for now: bidirectional transport is the CRDT-era decision; nothing here needs client→server frames. Interest declaration is rare and REST-shaped (below). SSE is one-way, auto-reconnecting, and already supported by NestJS `@Sse` on the existing Express server (ADR-0008).
- **Per-resource SSE endpoints (`/entities/:id/events`) instead of one multiplexed stream** — rejected: cleaner access control and lifecycle, but a workspace holding an arbitrary number of Entity tiles (a near-horizon feature) blows past the HTTP/1.1 six-connection-per-origin cap, and we can't assume the operator's reverse proxy offers HTTP/2. One multiplexed per-tab connection avoids betting the architecture on HTTP/2.
- **Refetch-on-focus/navigation with no push at all** — adopted *for the bare World Index list* (`/`), rejected for everything under active view: it cures fetched-once staleness cheaply but cannot deliver live-follow while a surface sits open. The bus covers resources being *viewed*; the Index list just refetches on focus.
- **Server-side event log with `Last-Event-ID` replay** — rejected: a nudge is an idempotent invalidation, not a fact you must not lose. Missing one means "stale until the next nudge or reconnect." On every (re)connect the client refetches its whole interest set, which heals any gap; the server remembers nothing.
- **Full-set reconciliation on every nudge** — rejected in favour of **delta**: re-reporting every subscribed resource on each event re-runs the access check for all of them (a 50-tile workspace, 50 evaluations per nudge). Delta pays ACL cost only for what changed; reconnect-refetch handles gap-healing.

## Consequences

- **Transport & fan-out.** One multiplexed SSE stream per tab: `GET /api/events`. Its first event mints an unguessable `connectionId`. The Instance is a single API process (ADR-0036), so fan-out is an in-process `EventEmitter`/rxjs `Subject` and the server holds only an in-memory `Map<connectionId → {principal, interest, stream}>`. **Ceiling:** a multi-process Instance would need a shared broker — out of scope while ADR-0002/0036 hold single-process.
- **Interest is client-owned and declared out-of-band.** SSE can't carry client→server messages, so the client declares what it's watching via `PUT /api/events/:connectionId/interest { refs: [{kind:'entity'|'world', id}, …] }` — the whole set, idempotent. A World is just another `ref`, so pin-order/rename/metadata changes flow as world-detail nudges; there is no separate worlds channel. The `PUT` is authorized to the same principal that opened the connection (`connectionId` is unguessable *and* ownership-checked) so one tab cannot set another's interest.
- **Principal is cookie *or* Public Link token.** Live-follow includes anonymous Public Link viewers — the highest-value audience (players watching a shared World). Rights on both the SSE open and every emit resolve through the existing single access seams (`acl/entity-access.ts`, `acl/world-access.ts`), which already resolve anonymous grants for `GET`s.
- **Emit-time ACL shapes the payload per recipient — it does not gate recipients.** On a change, the fan-out goes to *every* connection subscribed to that resource; each recipient's entry is computed against *their own current* rights: authorized → `{ id, version }`, else → `{ id, unavailable }`. This delivers **live eviction**: flipping an Entity to `private`, revoking a link, removing a member, or deleting all ride the same mutation event, and a follower who lost access gets `unavailable` in that nudge and blanks the view. Because rights are re-derived per principal, a follower holding a *separate* entity-level grant keeps following the now-`private` Entity while a world-share follower is evicted — one event, correct per person.
- **`unavailable` is opaque and carries no version.** Unauthorized, deleted, and never-existed are indistinguishable, so the status can't leak "it still exists, you just can't see it." Subscribe-time treats forbidden and nonexistent identically (both silently not-subscribed), so nobody can probe existence by subscribing to guessed ids. A recipient only ever gets `unavailable` for something they validly subscribed to and had access to — i.e. only about *their own* access ending.
- **Delta emission.** A nudge is an array of per-resource status entries (`[{id, version} | {id, unavailable}]`) containing only the resource(s) whose event fired. Reconnect → refetch-the-interest-set reconciles any missed events.
- **Client reconciliation.** Newer version than held → **debounced refetch, ~100–200ms per resource id** (independent timers, so unrelated resources don't wait on each other). `unavailable` → blank the view and prune the ref from the interest set. `version` plus `updatedAt` in the nudge dedupe self-echo and cross-tab echo (a tab already holding that state ignores it) without the server tracking who originated a change — `updatedAt` is what lets a metadata patch (rename, visibility), which never bumps `version`, still read as newer than held.
- **No new conflict machinery.** The nudge handler branches on the existing `dirty()` computed in `EntitySession`: clean buffer → refetch-and-replace silently; dirty buffer → **do nothing** (`if (dirty()) return`), so a background event can never clobber unsaved edits. Editors still discover concurrent edits at save-time via the existing 409/`_conflict` path (`entities.service.ts` version-checked `UPDATE`). The nudge's only obligation around a dirty editor is not to destroy their work.
- **Emit points are the write path, not controllers.** Entity save (version bump), rename, visibility change, delete, and World rename/pin/metadata/membership/delete each emit one change event into the bus from the service layer — one choke point per resource kind, mirroring the single access seam.
- **Dead connections must be reaped.** The in-memory connection map leaks if a client vanishes without a clean close (crashed tab, dropped network, killed proxy). The server sends a periodic SSE heartbeat/comment and drops any connection whose write fails or that has not been seen within a timeout window; the client's auto-reconnect re-establishes the stream and re-declares its interest set. Without this the map grows unbounded over an Instance's uptime.
