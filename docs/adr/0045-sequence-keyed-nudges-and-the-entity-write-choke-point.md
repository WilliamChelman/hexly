# Sequence-keyed nudges, and one write choke point per resource

Every Entity and World carries a **`seq`** — a monotonic counter bumped by _every_ committed change, whatever its kind: substance, exposure, sharing, lifecycle. It is the sole freshness key for live-follow, so a nudge shrinks to `{ id, seq }` and a follower refetches exactly when a nudge's `seq` exceeds the one it holds. All writes to `entities` and `entity_grants` route through a single **`EntityWrites`** module, and all writes to `worlds` and `world_members` through its peer **`WorldWrites`**; each owns the `seq` bump, the derived indexes, and the post-commit emit — so a write _cannot_ land without nudging. This revises ADR-0044 on three counts and fixes two defects it caused.

## Why: the two defects were specified, not merely coded

ADR-0044 enumerated its emit points as _"Entity save (version bump), rename, visibility change, delete, and World rename/pin/metadata/membership/delete."_ The World list includes **membership**; the Entity list stops at `delete`. Entity grant and owner changes were never in the spec, and the implementation faithfully built what was enumerated. Two consequences shipped:

1. **No eviction on revoke.** `removeGrant` deleted the row and returned. A Viewer live-following a `private` Entity through an entity-level grant kept following it after the grant was revoked — the precise scenario ADR-0044's live-eviction promise exists for.
2. **Rights never refreshed.** An Editor demoted to Viewer kept rendering a Save button, because `rights` ride the resource (ADR-0039) and nothing told the follower to refetch.

The structural cause is that `emitEntityChange(id, version, updatedAt)` demanded two facts an ACL mutation does not possess — a grant change touches neither column — while its World twin, `emitWorldChange(id)`, asked only for an id and was correspondingly never skipped. **The shallow interface caused the omission.** Both defects are now unstatable: `EntityWrites.mutate` is the only way to write, and it always emits.

### The same defect, one level up

`emitWorldChange(id)` being unskippable was not enough, because the World's membership set is not only the World's own access surface. Entity access reads `owner ∨ grant ∨ (shared ∧ world-member)` and Entity _write_ reads `owner ∨ (shared ∧ world-owner)`, so **every** `world_members` mutation moves some principal's Rights on the World's `shared` Entities. `worlds.service.bumpAndNudge` bumped the World and stopped: promoting a member to World Owner left them live-following a shared Entity with a read-only `rights` array and no Save button, and removing a member left them following an Entity they could no longer read. Defect 2 exactly, reached by a different road.

Emitting the Entity nudges without bumping their `seq` would have been a half-fix — the option this ADR already rejects below. A still-reachable follower's freshness gate drops a nudge at the `seq` it holds, so its `rights` stay stale; only the eviction path (which carries no `seq`) would have worked. So the membership write bumps `seq` on each shared Entity _and_ nudges. `WorldWrites` is where that fan-out lives, and the reason it exists as a module rather than a convention on the service: nothing structural forced the second half, so nothing performed it.

## Why a counter, and not `updatedAt`

`version` and `updatedAt` were doing three jobs between them. `version` is an optimistic-concurrency token: it guards `save`'s atomic `WHERE` and must **not** bump on metadata or sharing changes, or sharing an Entity mid-edit would 409 the editor's in-flight save. `updatedAt` is a domain-visible modified timestamp, rendered as "edited {date}" and used for `ORDER BY` in the Entity Browser and the World Dashboard. Neither is a freshness key — live-follow improvised one by comparing the pair, which is why a sharing change had nothing to say. `seq` names the missing concept.

`version` and `updatedAt` therefore leave the wire entirely. `version` still rides `EntityDetail`, because the client sends it back on save.

## Revises ADR-0044

- **Nudge payload.** `{ id, version, updatedAt }` → `{ id, seq }`; `WorldNudge` likewise. `{ id, unavailable }` is unchanged — eviction stays opaque and version-free.
- **Emit points.** The Entity list gains grant and owner changes, and the World's cascade-delete now emits per cascaded Entity (closing the deferral noted at `worlds.service.delete`). Emit points remain the write path, not controllers.
- **Dedupe rationale.** ADR-0044's _"`version` plus `updatedAt` … `updatedAt` is what lets a metadata patch, which never bumps `version`, still read as newer than held"_ is superseded: one counter bumps on every change, so no pair-wise comparison is needed. This also removes a latent bug — two changes within the same millisecond produced equal `updatedAt`, silently dropping the second nudge.

ADR-0044's central thesis — nudges carry no data, the authorized `GET` stays the single read path — is untouched and is what makes this change cheap.

## Considered Options

- **Bump `updatedAt` on every change, add no column** — rejected. It is what `worlds.service.touchAndNudge` does today, and what `patch()` already does on a visibility flip, so "edited just now" already lies for exposure changes. Extending the lie to sharing means a GM who shares thirty Entities before a session sends all thirty to the top of "Recently edited" — at exactly the moment they are reading that list. Access changes now bump `seq` only, which _fixes_ the existing exposure wart rather than generalising it.
- **Keep `updatedAt` as the freshness key and add `editedAt` for display** — rejected. The Unix `mtime`/`ctime` split, and the same one-column cost, but the new column is the user-facing one: it needs a backfill, all four read sites must move to it, and an existing field silently changes meaning. `seq` leaves `updatedAt` alone.
- **A content hash instead of the `version` counter** — rejected. A hash's correctness is a per-column obligation: `save` writes `document`, `contentText`, and `tags`, so a document-only hash loses concurrent tag updates, and any column added later escapes the hash unless someone remembers. A counter bumped at one choke point cannot escape — the same argument that motivates `EntityWrites`. It also buys nothing here: two clients making an identical edit still conflict, because the check compares the base they loaded, not the result they produced.
- **A server-sent version-free "refetch me" pulse** — rejected. `StaleNudge` is deliberately client-minted only, never a server frame, so followers reconcile reconnect gaps without the server remembering anything. Emitting it server-side would breach that.
- **Emit on ACL changes without a freshness key** — rejected as a half-fix. Eviction would work (`unavailable` carries no version), but a still-reachable follower whose rights changed would have its nudge dropped by the freshness gate and keep a stale `rights` array.
- **Scope `seq` to Entity, leave World on `updatedAt`** — rejected. The two kinds would stay asymmetric, `FollowStoreConfig.isNewer` would survive as a per-kind knob purely to paper over it, and the World Index would keep reordering when a member is added.

## Consequences

- **`EntityWrites` holds the only write handle** to `entities` and `entity_grants`. A lint rule bans `update(entities)` / `insert|delete(entityGrants)` elsewhere, in the idiom of the existing raw-`immer` ban. `worlds.service`'s cascade and `admin.service`'s grant purge — previously direct writers — go through it.
- **`WorldWrites` holds the only write handle** to `worlds` and `world_members`, guarded by the same lint rule under a second name. Its `membership(id, fn)` runs the ACL write, bumps the World's `seq`, nudges, and then fans out to the World's `shared` Entities via `EntityWrites.bumpWorldShared` — so a World Owner promotion refreshes Rights on the Entities it grants them, and a member removal evicts. `mint`/`update`/`delete`/`purgeMembershipsOf` cover the rest; `worlds.service` keeps the invariants (≥1-Owner, no-such-user, owner-wins upsert) and reaches for the handle, in the same split as `AclWriter`. The World path deliberately does _not_ fan out on rename or pin reorder: curation moves no Entity's Rights.
- **The transaction and the outbox are one seam, `WriteOutbox`**, shared by both handles — a membership change moves two resource kinds at once, and their nudges must flush from one commit or a rollback would strand half of them. It deduplicates ids on flush: one action may touch a resource twice (a nested `mutate`, a World that is both re-shared and renamed), and a follower learns nothing from a second byte-identical `{ id, seq }` frame.
- **The write kinds _are_ the Rights verbs.** `mutate(userId, id, { kind })` takes `edit | set-visibility | manage | delete`, so the kind determines the predicate: `edit` → `canEditSubstanceEntity`, `set-visibility` and `delete` → `canWriteEntity`, `manage` → Owner-only. This deletes `patch()`'s `changesVisibility ? writeFilter : editFilter` ternary — the caller no longer decides which rule applies to it. System writes (`cascadeDeleteWorld`, `purgeGrantsOf`) take no `userId` and are structurally distinct from user writes.
- **Nudges queue in a post-commit outbox.** Emitting inside a transaction would tell followers to refetch a version a rollback then erased, and because their held `seq` never advanced, nothing would later correct it. `WriteOutbox.transact(fn)` owns the outermost transaction and flushes on commit, dropping the buffer on rollback. This is safe as a plain array on a singleton **only** because `better-sqlite3` is synchronous — `transact` must therefore reject async callbacks at the type level, not by convention. A multi-process Instance would need a real outbox, alongside the shared broker ADR-0044 already names as its ceiling.
- **`emitEntityChange(id)` looks up its own `seq`** and short-circuits when nobody is following, mirroring `emitWorldChange`. A missing row is not an error — it is the eviction path, so a cascade-deleted Entity fans out `unavailable`.
- **One derivation, one place.** `contentText` and `descriptors` are both derived from Content, but `insertEntity` computed only the first, so created and imported Entities contributed nothing to the `::` Link Descriptor vocabulary. `EntityWrites.derive(content)` returns both and is the only caller of `extractText` and `harvestDescriptors`. The boot backfill that repaired pre-FTS `content_text` rows is deleted: it compensated for the gap this closes, and nothing is in production to repair.
- **`FollowStoreConfig.isNewer` is deleted.** It existed only because Entities compared `(version, updatedAt)` and Worlds compared `updatedAt`. With one `seq` on both, the two implementations are identical and the comparison moves inside `FollowStore`. One adapter becomes zero.
- **A table-driven spec enumerates the kinds** and asserts each emits exactly one nudge, so a fifth kind added without an emit fails CI. The grant-revoke eviction that ADR-0044 promised and never tested now has an end-to-end test through SSE, as do the two World-membership fan-outs: a promoted World Owner's shared-Entity follower is nudged with a bumped `seq` and refetches `edit` Rights; a removed member's is evicted.
- **The freshness gate is `seq` on every consumer.** `EntitySession.newerThanHeld` compared `(version, updatedAt)` and so dropped precisely the seq-only nudges this ADR introduces — the FollowStore refetched the fresh detail and the session threw it away. A consumer that gates on anything but `seq` reintroduces defect 2 in the client.
- **Ceiling.** `seq` is per-resource, not global, so it orders changes to one Entity and says nothing across Entities. Nothing needs a global order today; a cross-resource cursor (an event log, `Last-Event-ID` replay) would, and ADR-0044 rejected that on purpose.
