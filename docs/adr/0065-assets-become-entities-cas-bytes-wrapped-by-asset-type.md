# Assets become Entities: CAS bytes wrapped by a plugin-shipped asset type

Asset management (a browse/search page, sharp-derived stats, future AI tagging, future kinds — PDF, audio) needs search, facets, tags, rename, rights, and usage tracking — which is, line for line, the Entity feature list (ADR-0025 browser contract, ADR-0035 FTS, ADR-0055 facet harvest, Tags, the Owner model, the link index). We reverse the original stance and wrap each stored file in an **Entity** of `core.type.asset` (shipped by a new bundled `asset` plugin) rather than growing a parallel search/facet/rights system over the `assets` table. **Asset the storage layer is untouched**: bytes stay content-addressed on disk and served by the unauthenticated capability URL exactly as ADR-0034 decided — the Entity is the management handle over them.

## Decisions & consequences

- **The type**: one `core.type.asset` for every kind, defaulting the asset-ref Field (`core.datatype.asset` — `{hash, ext, mime, size, stats}`) and canonical **Content** (prose about the asset). Kind (image/pdf/audio) is a facet derived from mime, not a type; a kind splits into its own type only when it needs its own Field set (e.g. audio wanting `artist`). The one View dispatches on mime — image renderer today, icon-card fallback otherwise; PDF/audio renderers are later view-internal additions. Payoff: a Board **Embed** of an Asset transcludes its View, so future kinds land on Boards with zero new machinery.
- **Two access layers, deliberately distinct**: the Entity (document, discoverability, prose) is under the ordinary sharing model; the bytes stay capability-served with no auth (ADR-0034's accepted trade-off, unchanged). Stricter than before — metadata gains real ACL — but never uniform: visibility governs _finding_, not _fetching_.
- **Mint-and-dedup on upload** (reconcile-style, cf. ADR-0060, keyed on `(worldId, hash)`): re-uploading identical bytes returns the existing Entity — first name sticks. Name = filename stem; the extension is pinned in the asset-ref, so rename is plain Entity rename and **the URL can never move**. Uploader is initial sole Owner; default visibility `shared` (you upload for the World; `private` = "only in my picker"). Contributor-gated, as Entity creation always is.
- **Deletion is the Entity model** — no bespoke rights. Deleting the Asset deletes the bytes (dedup guarantees one Entity per hash — no refcounting); references degrade to dangling placeholders like any dead link, and re-uploading the same bytes heals them (same hash, same URL). Usage-aware confirmation is pure UI over inbound links, its named list per-viewer filtered like any backlink read.
- **References stay capability URLs** in Content `src` and Board Image elements — the URL is content-addressed, i.e. already an immutable id, so no editor changes and no document migration. The harvest resolves URL → hash → Entity into ordinary link edges; usage/orphanhood is just inbound links.
- **Stats and thumbnails are write-time mechanical extraction** (sharp for `image/*`; the extractor registry is an internal seam keyed by mime, _not_ a Plugin contribution point yet): stats into the asset-ref (dimensions, orientation, dominant color — facet-harvested per ADR-0055), one ~400px WebP thumbnail per image stored beside the bytes at a hash-derived path. A thumbnail is a regenerable cache, **not** an Asset — no row, no identity; original is the fallback. Extraction failure is non-fatal (`stats: null`, no thumb). **Augmentations** (AI description/tags via a future Ollama plugin) are the async, interpretive tier — that plugin is when the extractor seam grows a Plugin contribution point (beside `importers`, ADR-0053). One idempotent backfill job re-runs extraction over existing Assets.
- **No asset-naming special cases in surfaces**: the Entity Browser exclusion is a generic Type Definition capability (hidden-from-default-listing) the asset type sets; the World Graph shows Assets as ordinary nodes and gains a generic show-orphans toggle (default hide); Dashboard recents, Quick Open, and pins treat Assets like any Entity. The **Asset Browser** page is the Entity Browser preset to the asset type.
- **Vault IO is lossy binary passthrough** (ADR-0033's posture): export writes the file under `name + ext`, dropping prose/Tags/visibility — no sidecar `.md` convention invented now. Import mints through the ordinary path (stats inline); re-importing an export re-mints by hash, so URLs and references heal.
- **The `assets` table dissolves into a derived index** (`(worldId, hash) → entity`, the `entityImportSource` pattern — never a source of truth, rebuilt by Reindex) serving upload dedup and harvest resolution. Byte serving still reads disk directly, no table consulted. **No data migration**: pre-prod, the table just drops; dev data regenerates via vault import.

## Considered Options

- **Keep Asset a non-Entity concept with its own enriched table + bespoke search API** — the initial design, fully worked: paginated search endpoint with facet counts, LIKE→FTS5 upgrade path, usage-split delete rights (Contributor deletes unused, Owner deletes used), curatable name column. Rejected once AI tagging entered scope: it re-implements search, FTS, facets, tags, _and_ rights in parallel — the pattern this codebase consistently refuses (one document model, one write choke point, one facet mechanism). Kept as the documented fallback if entity-hood's exceptions ever metastasize.
- **Per-kind types now** (`asset.type.image`, `asset.type.pdf`, …) — rejected as speculative registration; the only kind-specific behavior today is rendering, which lives in the one View's mime dispatch. The split is additive later via the multi-type system.
- **Reference Assets by Entity id from prose/Boards** — rejected: the capability URL is already immutable and content-addressed; ids would force editor changes and a document migration for no stability gain.
- **Entity-per-upload without hash dedup** — rejected: twins with diverging names/prose over identical bytes, and delete would need refcounting before touching disk.
