# Decor Links: edge-level classification splits relation surfaces from usage surfaces

Assets-as-entities (ADR-0065) put every Asset on the World Graph as an ordinary node and let Thumbnail links (ADR-0066, an ordinary entityLink field) surface as outbound References — presentation plumbing polluting surfaces that exist to show _worldbuilding relations_. Rather than hiding assets per type, we classify the **edges**: a **Decor Link** is a link that exists for presentation and carries no worldbuilding meaning, declared where the edge is born. Relation surfaces subdue decor by default behind a reveal control; usage surfaces count everything, always. Assets then fall out of the graph as a _consequence_ — their inbound edges are decor, so they are orphans under the existing toggle — with zero asset-specific code. This amends ADR-0065's "the World Graph shows Assets as ordinary nodes" stance.

## Decisions & consequences

- **The producer declares decor-ness**, at three authoring points: a flag on Field definitions (`core.field.thumbnail` sets it; the flag lives in the shared Field schema and the World-scoped field editor exposes it as a checkbox, so a user-defined "Portrait" field doesn't re-flood the graph); capability-URL references (an image in prose, a Board **Image**) are decor **by construction** — a byte-serving URL is always presentation; prose Entity Links and Board **Embeds** are always semantic — including an Embed of an Asset, because embedding is a curatorial act where a thumbnail is not.
- **The "stored but surface-less" special case retires**: asset-hash edges stop being bespoke-invisible in the references read and become ordinary edges that happen to be decor — hidden by default, _revealable_ on both the References panel and the graph. Images referenced in prose are thereby handled, not hidden.
- **Relation vs usage is the surface split**: the References panel's outbound section ("References" — what does this Entity say about the world?) and the World Graph hide Decor Links by default behind a reveal ("show decor links", beside the graph's orphans toggle). The inbound section ("Referenced by" — where does this Entity appear?) shows every edge unconditionally, decor visually marked, never filtered: it is the usage reading that delete-confirmation (ADR-0065) is built on. The asymmetry is what lets an Asset's usage list work with **no asset special case** — it's just the inbound section doing its job.
- **Materialized at harvest**: the link index (ADR-0046) gains a decor flag written when edges are harvested, rebuilt by Reindex; existing edges classify on the next reindex. Read paths filter on the column — no per-read reclassification.
- **Reveal controls are ephemeral**, default hidden — a peek, not a mode worth roaming across devices.

## Considered Options

- **Type-level graph hiding** (a per-type "hidden from derived surfaces" capability, generalising `hiddenFromDefaultListing`) — rejected: it hides the _node_, not the _reason_. A user-defined portrait entityLink field would re-flood the graph with asset nodes the capability can't reach, and non-asset decor (a future banner link) would need the type flag too. The edge carries the meaning; classify the edge.
- **Keep capability-URL edges surface-less** — rejected: invisible-by-fiat can never be revealed; "which images does this page use" is a legitimate outbound question once a control exists.
- **Filter the inbound section too, with an exception for Assets** — rejected: a per-type exception is exactly the special-casing this design removes, and a usage surface that hides usage lies to the delete confirmation it feeds.
