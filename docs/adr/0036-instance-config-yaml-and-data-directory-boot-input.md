# Instance config in `hexly.yml`; an Instance Directory is the boot input

Instance settings were hardcoded in source — the vault-import upload ceiling (`worlds.controller.ts`, 100 MB) and decompressed ceiling (`vault-import.service.ts`, 256 MB) — with feature flags coming next, i.e. a _growing_ set of operator-facing knobs. We give a self-hosted **Instance** an **Instance Directory** as its boot input (`HEXLY_DIR`, replacing `HEXLY_DB_PATH`; named for holding both data and config) holding both `hexly.db` and an **Instance Configuration** file, `hexly.yml`, beside it. `hexly.yml` is the **single source** for these settings: a missing or partial file falls back to built-in defaults, an **invalid** file **fails boot** with the offending key named (zod), and there is **no env-var override** — each setting has exactly one home. Config is read once at boot by a `@Global` provider that mirrors `DbModule` (`useFactory: () => loadConfig(resolveInstanceDir())`), and the multer `fileSize` limit reaches its decorator via `MulterModule.registerAsync` injecting that provider — so no decorator ever reads config.

## Considered Options

- **Two env vars (`HEXLY_MAX_UPLOAD_BYTES`, …) instead of a file.** The lazy answer for two scalars, and rejected only because feature flags are next: the file will accrete, and a self-hoster editing one documented YAML beats a growing wall of `HEXLY_*` vars. Below ~two settings this would have won.
- **Keep `HEXLY_DB_PATH`, derive `hexly.yml` as the db file's sibling** (`join(dirname(dbPath), 'hexly.yml')`). Zero breaking change and it literally satisfies "config next to the db." Rejected because the app has no consumers but the author yet, so the breaking change is free now, and a folder-as-input is the cleaner mental model and the natural future home for on-disk assets (not yet stored).
- **Env-var overrides layered over the file.** Rejected: dual-source precedence for the same key is flexibility no one asked for and rots. Infra stays env (`PORT`, `HEXLY_DIR`, `NODE_ENV`); settings stay YAML. No overlap.
- **A plain memoized singleton `getConfig()` referenced directly in the `@UseInterceptors` decorator.** Tempting because config is a synchronous boot-time read, and it sidesteps DI. Rejected once `MulterModule.registerAsync` was confirmed to remove the decorator-timing problem the singleton existed to dodge: the DI provider is more consistent with `DbModule`, has no import-order fragility, and is trivially mockable.
- **Per-route inline multer limit / custom mixin interceptor / post-upload size check.** Rejected: `MulterModule.registerAsync` sets global `limits` that `FileInterceptor('file')` inherits (local-wins merge, verified against Nest's FileInterceptor source), it's the idiomatic path, and multer/busboy already enforces `fileSize` _during streaming_ (memory bounded) — a post-upload check enforces at a strictly weaker layer.

## Consequences

- **`HEXLY_DB_PATH` is retired for `HEXLY_DIR`.** `resolveDbPath` derives `hexly.db` inside the folder returned by `resolveInstanceDir`; `hexly.db`/`hexly.yml` are fixed filenames. `docker-compose.yml` (`/data`) and the three `package.json` scripts (`hexly-data`) are one-word edits; the seed CLI shares `resolveInstanceDir` so both entry points agree on one folder.
- **`:memory:` hatch preserved.** `HEXLY_DIR=':memory:'` → in-memory db + all-default config with no disk read, so tests and the CLI stay file-free.
- **Human-readable sizes, raw/processed split.** Values are written `500mb`/`5gb`, parsed by a ~5-line in-repo size parser (with one assert self-check) — no dependency; `yaml` and `zod` are already present. Config has two types: `HexlyConfigRaw` (the literal validated YAML, sizes as strings) and the app-facing `HexlyConfig` (sizes as bytes); a `processConfig` step maps one to the other, the single home for size-parsing and any future derived values, so no consumer re-parses `"500mb"`.
- **Defaults are generous for image-heavy vaults.** Seeded from the old hardcoded values, then raised: `maxUpload` 100→500 MB (an image-heavy vault balloons the _compressed_ upload, since assets ride inside the `.zip`) and `maxDecompressed` 256 MB→5 GB (it meters only inflated markdown — assets are skipped — so a real vault never approaches it; it's a high zip-bomb backstop).
- **Wiring.** `ConfigModule` (@Global, mirrors `DbModule`) provides the parsed config; `worlds.module` gets `MulterModule.registerAsync` and the decorator loses its inline `limits`. The unzipper is wrapped in an injectable `VaultUnzipper` facade that holds the decompressed ceiling from config, so `VaultImportService` calls `unzip(archive)` without threading the limit; the streaming logic stays in the now file-private `unzipVaultNotes` and `MAX_DECOMPRESSED_BYTES` is dropped.
- **`strictZipGuard` trades import speed against zip-bomb airtightness (default off).** The airtight path streams the archive and meters _actual_ decompressed output, aborting a bomb mid-inflate — but fflate's streaming inflate is ~5× slower than its batch `unzipSync` (measured ~5.6 s vs ~1 s unzipping a real 1200-note vault). With `strictZipGuard: false` (the default) the unzipper uses `unzipSync` with a filter that never decompresses junk (`__MACOSX`, `.obsidian`, non-importable entries) and trips the ceiling on the zip's _declared_ uncompressed size. That still catches an accidentally-huge vault and any standard bomb (which declares its true size), but a maliciously crafted archive can under-declare an entry that then fully inflates. We default to fast because the common deployment is a trusted personal/LAN instance importing the operator's own vault, where that attack is not a real threat; an untrusted or public instance sets `strictZipGuard: true` to restore mid-inflate metering. Both paths still enforce `maxDecompressed`; both hold the decompressed vault in memory (neither streams to disk), so the flag changes _when_ a bomb is caught, not the steady-state footprint.
- **Fail-fast is deliberate.** For a single-operator self-host, a typo'd limit silently reverting to a default is worse than a loud boot crash naming the bad key.
