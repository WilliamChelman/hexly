# The canonical Thumbnail Field is an entity link, not a capability URL

Any Entity — a monster, a deity, a Note — can designate an image **Asset** to stand in for it on tiles and rows (Entity Browser cards, Command Palette results, References). We add **one canonical Plugin field**, `core.field.thumbnail` (shipped by the asset plugin, the **Content** precedent — ADR-0051/0054), rather than a per-type nomination mechanism — and it stores an **entity link** (`{kind: 'entityLink', targetTypes: ['core.type.asset']}`), _not_ a capability URL. That sharpens ADR-0065's boundary into a rule: **an entity link is the reference primitive (what a typed Field stores); a capability URL is the render primitive (what an `<img src>` holds)**. Prose `src` and Board Images stay capability URLs — ADR-0065's rejection of entity-id references there stands untouched.

## Decisions & consequences

- **Why the entity link won**: it is a built-in — the picker, form control, write-gate target constraint, and edge harvest all exist, so there is no new Structured Data Type and no plugin form-control seam to invent. Usage surfaces as a _named_ inbound reference (asset edges are stored but surface-less), and a deleted target degrades to a legible dangling label. Given up: hash-healing — a capability URL survives delete + re-upload of the same bytes, an entityId does not; re-picking is one click, accepted.
- **Derivation is materialized, not read-time**: a derived nullable column on `entities` holding the target entityId, written at the write choke point (ADR-0045, which already holds the parsed document) and rebuilt by Reindex — never `json_extract` at read, because whole-World surfaces (future Graph avatars) must not parse every document. Reads join `asset_index` (entityId is its PK, ADR-0065) → hash → thumbnail URL: cascade-safe, never stale. `thumbnails=1` stays the opt-in emit flag on list endpoints. Pre-prod: no backfill; next save or Reindex fills it.
- **Precedence: the Field beats the Entity's own bytes** — an explicit designation over the implicit default. Later payoff: a PDF or audio Asset gets a hand-picked image tile.
- **Derivation pierces the Asset's visibility**: the emitted URL is a capability URL, and possession-reads-bytes is ADR-0034/0065's standing rule — filtering would punch per-viewer holes in shared cards. Visibility still governs _finding_ the Asset, exactly as before.
- **No Type defaults the Field** — attach-on-demand (ADR-0054/0057); any Type, plugin or user-defined, may opt in later via `fieldRefs`. Not required, not facetable.
- **Upload-on-the-fly is a generic control affordance, not a bespoke widget**: the core entityLink control offers pick-or-upload whenever `targetTypes` targets `core.type.asset` (web-core already owns the upload client; the Board picker's UX is the shared guts), so a user-defined asset-link field gets it code-lessly. The picker filters to image-kind Assets and previews via `thumbnailUrl`; mime is unenforced (forward-only) — a non-image designation just falls back to the type icon.
- **Vault IO stays lossy for the designation**: a frontmatter entityId dangles on import and sits inert (forward-only) — the same gap every frontmatter entityLink Field has today. The future fix is one frontmatter-converter extension to `VaultProjection` (ADR-0051), which repairs all such Fields at once; nothing thumbnail-specific is built.
- **External image URLs are rejected**: every property of the pipeline (the WebP rendition, usage edges, dedup) belongs to content-addressed bytes we host; an external image is one upload away via the picker.

## Considered Options

- **A capability-URL value via a new `core.datatype.asset-link` Structured Data Type** — fully walked: hash-derived column, `harvestEdges` → asset edge, healing on re-upload, plus a new plugin-contributed form-control seam (the first Structured Data Type with no View). Rejected: three new mechanisms re-implementing what the entityLink built-in already does, usage that never surfaces by name, and the access argument dissolved on inspection — the _served_ URL is capability-shaped either way, so storage gains nothing from being one.
- **A built-in `string` holding the URL** — rejected: bare string Fields harvest no edges, so usage would be silently missed unless `deriveDocumentState` sniffed every string value for URL shapes.
- **Per-type thumbnail nomination** (a Type maps one of its own Fields as the thumbnail source) — rejected: a second resolution path for every consumer, when Field reuse (ADR-0054) already lets any Type reference the one canonical Field.
- **Read-time `json_extract` derivation** — rejected once Graph avatars entered the picture: fine per page, wrong for whole-World fetches, and the write choke point extracts the key at marginal cost.
