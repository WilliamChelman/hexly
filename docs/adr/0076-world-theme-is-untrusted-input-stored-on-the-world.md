# A World Theme is a per-ColorScheme Palette stored on the World, treated as untrusted input

A **World Owner** may author a **World Theme** for their World: a **Palette** of ~10 anchors per **ColorScheme**, plus any individual token overrides, plus a radius set and a font pairing. It is stored inline on the World record, applied to `:root` through the CSSOM, and treated as **untrusted input** — because a **World Public Link** hands it to anonymous visitors who have no account and no relationship to its author. The token architecture it needs is ADR-0075; this ADR is the feature.

The binding constraint from ADR-0006 survives: **a World Theme and a reader's ColorScheme are orthogonal.** The Theme supplies palette identity; the reader still chooses Solar or Astral within it, which is why an Owner authors two anchor sets rather than one flat palette. A World Owner does not get to override a reader's day/night choice — that choice is closer to an accessibility preference than to decoration.

## What is themeable, and what deliberately is not

**In the contract:** colour, elevation, radii, and a font pairing chosen from a curated bundled set. Radii are the cheapest identity lever there is — sharp versus soft changes a World's feel for five values and no risk — and elevation must be in, because the shadows are warm-tinted to the paper (`rgba(60, 44, 22, …)`) and would otherwise keep a sepia cast in a crimson World. Fonts are curated rather than free-form: uploaded font files are mechanically possible via ADR-0065 assets, but that is a licensing, CAS-storage, `@font-face`-injection, and FOUT feature, and the token shape (`--font-display`, `--font-body`) is identical either way — so opening it up later is additive, not a redesign.

**Out of the contract:** the type scale, the layout rails (`--rail-*`, `--container-reading`), and motion. These are structure and behaviour, not identity: `--text-2xs` is 11px because coordinate chips need it, `--rail-inspector: 900px` is a bug rather than a theme, and motion is a reader's accessibility concern (`prefers-reduced-motion`), not an author's to set. **"Out" means not public, not "not a token"** — so `tokens.css` carries a real internal boundary, and the manifest (ADR-0075) is what makes it enforceable rather than aspirational.

That puts a complete World Theme at roughly **25–30 authored values**, against the ~90 the flat token layer would have demanded.

## Why untrusted

A **World Public Link** (CONTEXT.md) is an unguessable URL granting anonymous, account-less read access to a World's `shared` Entities. So an Owner's theme values execute in the browser of someone with no account and no trust relationship to that Owner.

Applying via the CSSOM already makes declaration injection impossible — a custom property's value cannot create new declarations, and a `var()` substitution that fails to parse is invalid at computed-value time. Injecting a `<style>` block would be strictly worse, adding `red } body { display:none } x {` on top. But neither closes **value abuse**: `background: var(--gradient-gold)` is a real declaration in `button.component.ts`, and `url(https://evil.example/p.png)` is a perfectly valid `background` value. An Owner could set that stop and collect the IP, user-agent, and visit timing of every anonymous visitor — people who deliberately have no account.

So values are **typed**. Every themeable token has a declared type in the manifest, and values are parsed and re-serialised to a canonical form at the write choke point (ADR-0045), the same place `terrainIdSchema` already constrains stored ids. A colour token accepts a colour and emits a colour; `url()` never round-trips because it is not one. The `@property` registration from ADR-0075 is the second line: Blink discards an invalid `setProperty` on a registered property outright, so the platform re-checks what our schema asserted. The typed schema pays for itself outside security too — it is what lets the editor render the right control per token, and what makes "the contract" an artifact rather than a comment.

## Decision

- **Storage is inline on the World record** — a `theme` field patched wholesale through `PATCH /worlds/:id`, exactly as `pinnedEntityIds` already is. Reuse across Worlds is "copy from another World" in the editor: a duplicate, not a link.
- **Resolution chain: instance default → World Theme → reader's ColorScheme.** The instance layer lives in instance-config YAML (ADR-0036), not the World table — same anchors, same manifest, different source — and ships empty. An operator wanting to brand their deployment is the first thing that will be asked for after this lands. (**Built in #372** as a `theme` block, detailed in the spec. It departs from `hexly.yml`'s strip-unknown rule (ADR-0052) and makes the loader report _every_ offending key rather than the first, both because "reported at boot rather than applied half-way" is the acceptance criterion and a silently stripped anchor fails it.)
- **The theme is served on the unauthenticated World read path**, because Public Link visitors must receive it. It is therefore readable by anyone holding the link. That is presentation data and acceptable, but it is a conscious call rather than something to discover later.
- **Applied at `:root`, via the CSSOM**, in the world-scope resolver. `:root` and not a subtree, because CDK overlays portal to `<body>` — a subtree-scoped theme would leave every menu, dialog, and toast unthemed.
- **Token declarations key off `[data-color-scheme]` on any element, not `:root[data-color-scheme]`.** This is what lets an offscreen probe carry the opposite ColorScheme and candidate anchors, so the editor can report contrast for the scheme the author is not currently looking at. Without it, half of every theme ships unchecked. (**Amended in implementation (#370, #373):** the widened selector carries **tier 1 only**, so the offscreen probe this bullet was written for reports the _active_ scheme's roles while looking like it reported the other one's. The reporter measures on the document root instead — see the spec's §5.3 amendment. The widening still earns its place: `hexlyPalette` reads Hexly's own anchors past a painted World Theme with it.)
- **Overrides are applied per ColorScheme.** An inline custom property on `<html>` beats both the light and the dark stylesheet rule, so the applier selects the active scheme's overrides and re-applies on toggle. `ColorSchemeService` already owns that swap.
- **The last-applied theme is cached in `localStorage` keyed by world id**, so a hard reload back into a World is flash-free. A flash on _first_ entry to a World is inherent: the pre-paint script in `index.html` can read a single unscoped key, but the world is not known until routing resolves (ADR-0028).
- **A theme edit bumps `seq`**, so a live-following reader (ADR-0044/0045) re-applies without a refresh. An Owner tweaking their palette while players watch is the demo that sells the feature.
- **Contrast: on-colours flip automatically, everything else warns.** The flip is silent and has no UI. Body pairs below 4.5:1 (`ink` on `surface`, `ink-muted` on `surface`, `accent` on `bg`) surface the computed ratio in the editor. **Nothing is hard-blocked** — this is a creative tool, a deliberately oppressive palette in a horror World is a legitimate choice, and a block just gets routed around by overriding a different token.
- **A corner may only take a step the manifest declares** (**added in implementation, after #375**), fenced by the `hexly-design/no-builtin-radius` lint rule — the radius sibling of `no-builtin-shadow` (ADR-0021). Bare `rounded` is a hard-coded 4px, and Tailwind's own `--radius-xs/-2xl/-3xl/-4xl` steps survive our `@theme`, so both render fine and neither follows an Owner's set: the failure is silent, which is the whole reason it is a lint rule and not a review note. `rounded-none` and a bracketed arbitrary value stay allowed — the first squares the corner outright, the second is a stated choice rather than the accidental default the rule exists to catch.

## Considered Options

- **A standalone Theme record referenced by Worlds.** Rejected. Its one real advantage — edit once, update many — is speculative until someone actually runs Worlds in lockstep, and its failure mode is worse than the duplication it saves: a shared edit silently restyling a World that a different Owner manages.
- **A Theme Entity.** Rejected structurally, not on taste. An Entity belongs to exactly one World, so a Theme Entity in World A cannot style World B; and it would put the theme behind the per-Entity access filter that an anonymous Public Link visitor must not be blocked by.
- **A single flat palette that overrides the reader's ColorScheme.** Rejected: it is cheaper for the author and it takes an accessibility-adjacent choice away from the reader, and it would end ADR-0006's "one identity at two times of day" as a system property.
- **Hard-blocking low-contrast themes.** Rejected, but not comfortably — see below.
- **Trusting World Owners.** Rejected on the Public Link alone. "The Owner is trusted" is a claim an anonymous visitor never agreed to.

## Consequences

- **Contrast can only be checked in a browser.** The derivation is CSS-side (ADR-0075) and the report comes from `getComputedStyle`, so the server cannot validate readability at the write choke point. A client that skips the warning stores anyway. Acceptable while the policy is warn-only, but it does mean the warning is advisory in the strict sense.
- **`contrast-color()` has a mid-tone blind spot we can detect but not fix.** MDN's own example is `#2277d3`, which yields black text that is not readable at small sizes — precisely the risk zone for a user-picked accent. The probe makes it _detectable_: read the resolved on-colour and its background, and if both black and white fail, say so plainly ("this accent is mid-tone; no automatic text colour is readable — pick lighter or darker"). CSS cannot resolve it.
- **The people harmed by a bad theme are the ones who cannot change it.** Anonymous Public Link visitors did not choose the palette and have no preference to override it with. The defensible floor, if the warning proves insufficient, is a per-reader "use the default theme" escape hatch that persists across Worlds — not a constraint on what an Owner may author. Deliberately not built now; this paragraph is why it would be cheap.
- **The eight categorical tones (ADR-0075) are a bigger public surface than they look.** With `-soft` variants that is 16 derived tokens, 16 manifest entries, and 16 `@property` registrations that a World Owner may have overridden and that therefore cannot be freely renamed.
- **An Owner who re-anchors the accent moves the whole categorical set with it.** The tones are hue rotations off `--color-accent`, so choosing a crimson accent rotates all eight — which is the coherence the derivation exists to give, but it also means the exclusion arc around danger and success was computed against Hexly's accent and does not automatically hold for theirs. The editor's contrast report should extend to a collision check against `--color-danger` and `--color-success`.
- **Every public token becomes a compatibility commitment.** The manifest is the versioned surface; adding to it is cheap, and removing from or renaming within it is a migration against stored World Themes.
