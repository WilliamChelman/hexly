# A mention mints a real Entity; the Unresolved Link stays an import artifact

Typing `@An Unknown Entity` in prose now **creates the Entity** and links it, rather than leaving a label pointing at nothing. The `entityLink` node has always allowed `entityId: null` (ADR-0023) and the Vault import mints them by the hundred for wikilinks that resolve to no note (ADR-0033), so a second, id-less flavour of Entity Link already existed — it was simply never authorable. We keep it exactly that narrow: a targetless link is an **Unresolved Link**, produced only by import, promoted in place, and never created by hand.

The choice is between one relation model and two. A real Entity is recorded by the edge index, drawn by the World Graph, counted by the Facet rail, found by FTS, and — the point — **offered by the `@` picker the next time the same name is typed**, so two notes mentioning "Zorblax" converge on one node instead of drifting into two spellings. An id-less label gets none of that without a parallel index, a parallel suggestion source, and a parallel promotion flow: a shadow Entity system beside the real one.

## Two knobs, because "the default Type" is two questions

Inline Creation reads `entities.inlineType` (default `core.type.note`) and `entities.inlineTag` (default unset), **separate from `entities.defaultType`**. The two answer different questions: `defaultType` is _"the user asked for an Entity — which kind do I make?"_, an operator's opinion about their campaign, while Inline Creation faces _"nobody has said what this is yet."_ Conflating them is not a tuning problem but a category error, and the repository's own e2e configuration proves it — `entities.defaultType: core.type.hex-map` is a supported setting, under which a name typed mid-sentence would mint a **Hex Map**. No single value makes both questions right.

`inlineTag` is the triage lever, deliberately opt-in and deliberately a **Tag** rather than a system marker: the operator picks the string, or picks none, so nothing is imposed on an author who does not want the bookkeeping. Set it, and the untriaged pile is one click in the Tag facet. Its ceiling is stated in the Consequences.

## The picker offers creating, not parking

With a non-empty query the `@` listbox appends two rows below the matches — **`Create "…"`** and **`Create "…" with details…`** — _always_ appended, even when matches exist, because "Jane Doe" already existing must not block authoring a second, different Jane Doe. On zero matches the plain Create is the active row, so `@An Unknown Entity` + Enter creates and links in one gesture and there is no state where Enter does nothing.

The details row opens the ordinary create dialog to set Types and Tags before minting. It is deliberately _not_ the fallback this design once carried (see below): a fallback is a modal the system forces on you, this is one you ask for, and the fast path is unchanged by its existence.

The fast path is silent and unconditional: same World as the host Entity, `inlineType` + `inlineTag`, and no modal the author did not ask for. That it is _unconditional_ is only true because **ADR-0074** demoted the required-Field gate. Under the old rule, `inlineType` being operator-configurable meant pointing it at a Type with an unmet required Field would `400` **every** silent mint, and this design carried a fallback to the create dialog to survive it. Absence no longer refuses a write, so any Type can mint and the fallback is gone. It is worth recording that this design reproduced, independently, the workaround already sitting in `new-entity-button.component.ts:124` — two designs bending around one gate is what got the gate removed.

There is no **Park** row. Declining to link is already expressible — type the name as plain text and press `Esc`.

## Import chooses which model it lands in, and defaults to the additive one

Vault import gains a switch, **defaulting on**: create the Entities its unresolved wikilinks name (under `inlineType`/`inlineTag`, like any Inline Creation), or leave them as Unresolved Links, which is today's behaviour. The switch is the whole triage story rather than a detail beside it — on, and every mentioned name is a real Entity, searchable, graphed, and offered by the picker; off, and the links stay inert in the prose, promoted in place when the author next reads that passage. An untyped `.md` file keeps landing on `defaultType`: it is a real note, not a mention.

It defaults on because an importer arrives with Obsidian's model, where an unresolved wikilink is a _visible_ to-write list rather than inert text; landing a first vault in the off state means the vault's intent silently does not survive the trip. Neither setting is a trap, which is what makes the choice free: a vault import **mints a fresh World** (`vault-import.service.ts:119`), so an import you dislike is undone by deleting that World and re-running with the switch flipped. Recoverability is at World granularity in both directions.

The dialog also exposes the Type and the Tag as **per-run overrides**, prefilled from `entities.inlineType`/`entities.inlineTag` and not persisted. That is what the two knobs are for: an instance-wide default that a user can see and override at the one moment a bulk decision is being made. The Tag is free text rather than a picker over the World's existing tags, because the World does not exist yet. `@` creation gets no such override — silent minting under the defaults is the point, and a single mention wanting a different Type is promoted afterwards, losslessly.

**The hook is one function.** `resolveLink` (`vault-import.service.ts:126`) is already the single seam every wikilink passes through. Auto-creation slots in on the miss: mint, **register the new Entity in the `NoteIndex` under that label**, return its id. Vault-wide dedup then falls out for free — the second note writing `[[Zorblax]]` is answered from the index, ADR-0033's case-insensitive basename matching intact, no extra pass. The `resolved`/`dangling` counters become `resolved`/`created`/`dangling`, which is also the summary line. A minted Entity takes the **basename** as its name, never an explicit path: `[[folder/Zorblax]]` names _Zorblax_.

## Considered Options

- **A dedicated `core.type.stub`** — rejected, after being adopted and reversed twice inside one design session, which is itself the finding. It bought exactly two things a Type gives for free: the `hiddenFromDefaultListing` exclusion, and a Type-facet bucket as a worklist. But a stub must be writable the instant it is opened — the whole point is that it is the page you are about to write — so it had to reference `core.field.content` and declare the Rich Content View, at which point it _is_ `core.type.note` wearing a flag. `inlineTag` recovers the worklist for one config line. Only the listing exclusion is genuinely lost (see Consequences).

- **Allow an empty `types` array and drop the concept** — rejected on measured cost. The Type facet counts through `innerJoin(json_each(types))`, which drops a zero-length array entirely, so untyped Entities would be _uncountable and unfilterable_ in the rail without a `LEFT JOIN` and a synthetic `(none)` bucket. `hiddenFromDefaultListing` resolves per type id through the registry, so an Entity with no type has nothing to hang an exclusion on. And roughly twenty non-spec sites read `types[0]` as non-optional — every picker, the header eyebrow, the Dashboard rows, Quick Open, the graph palette, `TypeRegistry.chromeLabel`/`resolveFields`/`viewsFor` — each needing both a null path and a hand-designed "no type" rendering. One Type registration supplies as data what that sweep would hand-write, and the empty set still fails the facet.

- **Id-less links as the default, promoted on demand** — rejected. It inverts the common case: most mentions are of things the author intends to write about, and it makes the ordinary act of naming something produce an object with no presence anywhere in the application.

- **An indexed parked label (`EdgeTargetKind: 'parked'`, `targetId` = the label text)** — rejected as machinery out of proportion to the case, though it fits the schema almost too well: `entityEdges` is polymorphic by design, `targetId` deliberately carries no FK, `worldId` is denormalized, and `(worldId, targetKind)` is already indexed, so the suggestion feed and a "47 names mentioned, never written" worklist would both have been one indexed read. It was cut with the affordance it existed to serve. The door is left open by ADR-0046's own framing (_"a future `map → asset` link slots in with no schema change"_), and the day a hand-authored targetless link returns, this is its shape.

- **A `stub` Tag applied by the system** — rejected. `CONTEXT.md` draws the Tag/Type line at _registration_ and holds that Tags carry no behaviour, so a system-assigned Tag is a category error, and a fixed string would collide with an author's own. `inlineTag` sidesteps both by being **operator-chosen**: the system applies a label the operator authored, which is a preference, not a marker.

## Consequences

- **An Unresolved Link is unlisted by construction, and that is the accepted ceiling.** Nothing indexes it: `richContentBase.harvestEdges` returns early when `entityId` is not a string, so no edge is minted (ADR-0046) and no read can enumerate them. With import auto-creation off, a vault carrying five hundred unresolved wikilinks yields five hundred links findable only by reading the prose around them. The import summary's resolved-vs-dangling tally (ADR-0033) stays a count, not a list. This is deliberate — the switch _is_ the answer, and an author who wants those names triageable turns it on — but it means the off path has no recovery surface, and a bulk "resolve these" screen would need the parked-label index above before it could exist.

- **A hand-authored targetless link becomes unreachable, and the model gets simpler for it.** Every Unresolved Link now has exactly one provenance, so "where did this come from?" has one answer, and `wikilinkToEntityLink` is the single site that mints one. Should the affordance ever return, it arrives with the index, not before it.

- **`inlineTag` can select the untriaged pile but never hide it.** Facet values OR within a category and AND across categories, with no negation — so the tag surfaces created Entities on demand and cannot exclude them from the default grid, which is the one thing `hiddenFromDefaultListing` would have done. This bites hardest on the default path: auto-creation is **on** and `inlineTag` is **unset**, so a freshly imported vault's Entity Browser holds every mentioned name mixed indistinguishably among the real notes, with no lever at all. Setting `inlineTag` is the whole mitigation, and nothing prompts an operator to set it. If this proves too blunt, the replacement is a reading over **Incomplete** (ADR-0074) rather than a second tag.

- **Inline Creation is a write, so it inherits create rights.** An **Editor** granted rights on one Entity is not a **Contributor** in its World, and cannot create Entities there. The Create row must therefore be absent — not present-and-failing — for a caller without create rights in the host Entity's World, which leaves that caller with pick-or-nothing. Parking would have been their escape hatch; plain text is what remains.

- **An Unresolved Link and a dangling one look different and afford different things.** Both render identically today, and they must not, because `EntityNameResolver`'s failed batch resolves _every_ id in it to `missing` — a network hiccup makes healthy links read as dead. So clicking an **Unresolved Link** (no id: a fact about the document, no fetch involved) offers both _Create_ and _Link to an existing Entity…_, while a **dangling** link offers only _Link to an existing Entity…_. Offering Create on a dangling link would let a bad connection mint a duplicate of an Entity that exists and is fine; retargeting is also the honest fix for a link that once had a target. Writers only — a read-only viewer keeps today's inert label.

  Retargeting matters more than it looks: ADR-0033 resolves wikilinks by case-insensitive basename, so an import routinely fails to match `[[Zorblax]]` against an Entity actually named "Zorblax the Devourer". Create-only would force an author to mint a duplicate of something they already have.

- **The details dialog must stop navigating, and the suggestion range must outlive it.** `CreateEntityDialogComponent.submit()` ends in `router.navigate(entityRoute(...))` (`create-entity-dialog.component.ts:209`), which is fatal from a mention — creating mid-sentence must leave you in the editor. It should `close(entity)` and let its caller decide, navigation being the World Index caller's concern rather than the dialog's. The World is likewise **locked** to the host Entity's, not offered as a select: minting into another World would author a cross-World link as a side effect of typing.

  The trap underneath is that `@tiptap/suggestion` fires `onExit` the instant the popup closes, so by the time a dialog resolves there is no live range left to replace — and `entity-mention.ts`'s `programmatic`/`picked` bookkeeping is already deleting ranges in that handler. The range is captured before the dialog opens and the link inserted against the stored one.

- **Cancelling the details dialog leaves the typed text, and that is the existing rule, not a new one.** `onExit` deletes a range only when `programmatic && !picked` — the `@` that `/link` inserted, never text a human typed. So cancelling behaves exactly like pressing `Esc` at the picker, and the invariant stays: _we clean up what we inserted, never what you typed._

- **Inline Creation is prose-only, and the Entity-Link Field pickers are excluded on semantics, not just scope.** A typed Entity-Link Field carries **target-type constraints** (the parameters live on the Field, and `linkTargetTypeErrors` enforces them), so creating from `entity-link-picker` would have to mint under _the Field's constraint_, never `entities.inlineType` — a Thumbnail Field minting a `core.type.note` would produce an Entity that instantly fails the Field that created it. Prose has no constraint to honour, which is precisely why a configured `inlineType` is the right answer there and the wrong one in a Field. That rule is recorded here so the day someone wants it, it is a design decision rather than a rediscovery.

- **Promotion is lossless because Field ids are document keys** (ADR-0056). Adding a real Type to an Entity created inline leaves its prose exactly where it is; only the type set changes. Nothing has to migrate a value from a stub shape into a typed one, which is the mechanical reason a configured `inlineType` costs nothing to get wrong.

- **A promoted Unresolved Link takes its `label` as the new Entity's name, never its `display`.** `[[Zorblax|the old wyrm]]` names an Entity _Zorblax_; the `display` attr is prose phrasing and stays on the link, still rendering statically per ADR-0033. The `heading` attr is carried through unchanged.

- **Two default Types are live in one import.** An untyped `.md` file lands on `entities.defaultType`; an unresolved wikilink, when auto-creation is on, lands on `entities.inlineType`. Coherent — one is a note the vault actually held, the other a name it only mentioned — but the two knobs sit adjacent in configuration and will read as a duplicate to anyone who has not read this.
