# Hexly ships as a Desktop App: Electron hosts the API in-process on loopback

Hexly has called itself a "desktop-style" app since ADR-0002, and ADR-0036 already made its boot input a _folder_. We now ship that literally: a **Desktop App** — an Electron shell whose main process boots the same Nest `AppModule` with `app.listen(0, '127.0.0.1')` and points a `BrowserWindow` at the resulting ephemeral port. ADR-0008's one-process-one-origin topology _is_ the desktop topology, unchanged: the same Nest process serves `/api`, the built SPA, and `/assets/...` capability URLs, so cookies, SSE live-follow (ADR-0044) and asset `src` attributes all keep working with no client fork. The Desktop App is **local-only** — it hosts its own Instance and can never point at a remote one; the browser already is the remote client.

## The session, and why loopback needs one

Main mints a session row for the **Sole User** at launch and writes `hexly_session` into the renderer's cookie jar (`session.cookies.set`) before `loadURL`, then revokes it on quit. `SessionAuthGuard` is untouched — it finds a genuine session — and the login page is never rendered.

Keeping a real credential is the point, not ceremony. **A loopback socket is not a security boundary**: `127.0.0.1` is not reachable from the LAN or the internet — that part is a genuine property of binding loopback rather than `0.0.0.0`, and it opens no firewall hole — but it _is_ reachable by every local process and, more importantly, by every web page the user visits, which can `fetch('http://127.0.0.1:<port>/api/...')`. The ephemeral port (`listen(0)`) means a page must scan ~16k ports to find us, which raises cost without being security.

Two walls make that acceptable, and they are load-bearing:

1. **The session cookie.** Electron's cookie jar is not the browser's jar, so an attacking page holds no token and gets a 401. "One user" never implied "no credential" — a guard that resolved the **Sole User** from an absent cookie would hand every visited web page the whole vault, which is why that option was rejected outright.
2. **The deliberate absence of CORS** (ADR-0008 adds no `enableCors()`). Even for an unauthenticated route, a cross-origin page cannot _read_ the response body.

DNS rebinding is the attack that pierces wall 2 — an attacker domain resolving to `127.0.0.1` makes the page same-origin — but it does not pierce wall 1, because the browser then sends cookies scoped to the attacker's host, not ours. In the desktop profile we additionally reject requests whose `Host`/`Origin` is not the loopback address we bound: cheap, and it closes rebinding at the door rather than relying on the cookie alone. Built (#321) as the **first** middleware in the pipeline, so neither a controller nor the SPA this same process serves answers a rebound request, and asked for by the entry point (`createApiApp({ loopbackOnly: true })`) rather than derived from the profile — a desktop-_profile_ server, which is what the browser e2e run is, is legitimately addressed as `localhost`. The address to expect is read off the connection (`req.socket`), so `listen(0)`'s ephemeral port needs no bookkeeping, and the rejection is a **403**: 401 is the one status the client answers by re-minting, and a caller at the wrong name has no session problem to fix.

Two things keep this in proportion. A local process running as the user can simply read `hexly.db`, so for _that_ threat the socket adds nothing filesystem access did not already grant; the socket's only novel exposure is the browser-page path, which the two walls close. And the category is not permanent — the `protocol.handle` option below removes the listening socket entirely, and remains the upgrade if this ever stops being acceptable.

Because identity is never in question here, a 401 is recoverable rather than fatal: the renderer asks main to re-mint through the preload bridge and retries. The condition is the **bridge's presence**, not a config flag — "can I renew?" is a capability question, so it gets a capability check (ADR-0071 draws the same line for policy questions). This matters because `authGuard` otherwise routes to `/login`, which in the desktop profile is a dead end: the Sole User has no password, so any 401 — expiry, a cleared jar, a replaced DB — would strand the user permanently.

Built (#321) as **one HTTP interceptor**, not a branch inside `authGuard`: a 401 is where a lapsed session actually shows itself, so a single retry there covers the boot `GET /auth/me` — putting the guard back in an authenticated state before it ever reaches its policy choice — _and_ every later data request, without the guard learning about the bridge at all. Because each re-mint revokes the session before it, a second renewal would revoke the session the first one's retries are carrying — so concurrent 401s share one round trip, and a 401 from _before_ the current session retries without asking again, which needs the client to count re-mints and each request to remember the count it went out under. Not covered: the live-follow `EventSource` and `<img src>` do not pass through `HttpClient`, so a stream that 401s reconnects on its own terms rather than being renewed.

## The Instance Directory is pinned; only assets move

The Instance Directory is `app.getPath('userData')/hexly`, fixed and not user-choosable. **The pin is the safety property.** ADR-0002 runs SQLite in WAL mode, and a cloud-sync daemon or network mount rewriting `hexly.db`/`-wal` underneath an open handle is a known corruption path — so the most popular choice a folder picker would offer (`~/Dropbox/Hexly`) is precisely the one that eats worlds.

Asset bytes are content-addressed and write-once (ADR-0034), so they are safe anywhere: a partially-synced or unmounted file degrades to missing bytes, never to a corrupt vault. They are also the bulk of the data. So `assets.dir` (see the ADR-0034 amendment) is the escape hatch, with a desktop picker that moves the bytes with progress, verifies by hash, rewrites `hexly.yml` and calls `app.relaunch()` — config is read once at boot, so applying it means a restart we own. Portability of the _authored_ substance stays the Vault export (ADR-0033), which is better in a git repo or a synced folder than a `.db` could ever be.

Built (#326) split down the middle, and the ADR-0034 amendment records why: main owns the picker, the copy, the `hexly.yml` write and the restart; the renderer owns the only surface a minutes-long copy can be watched and cancelled from, reached as a **Command** so the File menu and the Palette share one implementation. Three things fell out. The relaunch is `app.relaunch()` followed by `app.quit()` — not `exit` — so it still goes through the ordered shutdown below, and it is **delayed by a beat** so the outcome reaches the dialog before the window it is drawn in goes away. `ASSETS_DIR` is read off the running app through `apps/api/src/host.ts` rather than recomputed in main, so the folder offered for moving is by construction the one being served. And the affordance is gated on the **bridge's presence** rather than the profile, which is ADR-0071's own rule applied to the picker its cut list had filed under the profile.

## The native menu displays accelerators; the dispatcher owns them

An OS menu accelerator is consumed before the renderer sees the keydown, which would make the menu a second dispatcher — blind to `pushModalScope()` and to the editable-target gate, reintroducing exactly the bugs ADR-0063 was written to kill (a chord firing behind an open `<dialog>`). So menu items that duplicate in-app actions set `registerAccelerator: false`: ⌘K is _displayed_ in the menu but not bound, and the renderer's single dispatcher keeps ownership. A menu click IPCs into the renderer and invokes the **Command** — widening `Command` from a Palette entry to an invocable action with two surfaces. Genuinely native chords stay native roles (clipboard, zoom, reload, window, quit); the dispatcher never claimed those, and the clipboard roles must be registered or ⌘C stops working in web content on macOS.

Built (#322) as a pure template — `buildAppMenuTemplate(platform, actions)`, with `Menu.buildFromTemplate` left in the entry point so the structure is unit-testable without an Electron runtime — and the second surface is a **`CommandDirectory`**: Commands reachable by id, alongside the Provider registry the Palette searches. The bridge grows `onMenuCommand`, main sends an id, and the renderer invokes; opening the Palette is itself a Command, so the menu item goes through the same door as everything else. An id nothing holds is a warning, not a throw: the menu is built once at launch while a Command's availability is conditional (ADR-0071's cut lists). Three things fell out of building it. Electron sets `registerAccelerator: false` on the **clipboard roles itself** — macOS's text-editing responder chain is what delivers ⌘C to web content, which is the same fact from the other side — so the invariant a spec can own is that _we_ never turn a role's accelerator off, asserted over the whole template rather than the one item we ship. Menu labels are **English only**: main has no transloco catalog, and joining the two bundles' i18n for six strings buys less than it costs. And **Reveal data folder** lands here as `shell.openPath` on the pinned Instance Directory — the backup story in one gesture.

Alongside: a single-instance lock (two processes running boot migrations on one SQLite file is a race, ADR-0027), external links handed to the system browser via `setWindowOpenHandler` and a `will-navigate` guard (otherwise a link inside Content navigates the SPA away with no back button), window-state persistence, Electron's built-in spellchecker (the app is fundamentally a prose tool), and multi-window — coherent precisely _because_ live-follow was kept, so two windows on one Entity reconcile through the nudge bus.

## The window is a native window (#323)

Built as four small modules main wires together, so the decisions are unit-testable without an Electron runtime — the same shape `buildAppMenuTemplate` took.

**Links** reduce to one pure question, `linkDestination(url, appOrigin)`, with _three_ answers rather than two: `internal` (our own origin — routes, cross-World Content Links, `/assets/...` and the live-follow stream all live there), `external`, and **`refused`**, because Content is authored text and a `file:` or `javascript:` URL in it has no business being followed by this window _or_ handed to a browser. Both interception points are needed and they see different gestures, which is why both are wired. A `window.open` on one of _our_ URLs — the Palette's and the World Graph's modifier-click — is answered by `deny` plus a window we open ourselves rather than by Electron's `action: 'allow'`: an allowed window inherits the opener's preferences instead of being built the way every other window is built, and it would miss the geometry tracking and these same handlers.

**Geometry** is kept beside `userData`, deliberately _not_ in the Instance Directory: where a window sat is this machine's business, and the Instance Directory is the folder a user copies to back worldbuilding up. Only the launch's **first** window is remembered — that is what "per window where that makes sense" resolves to, and the alternative is a bug: every window sharing one file means a cascaded second window's bounds become _the_ remembered geometry, walking the reopening position a step down the screen for every second window ever closed. Two more things fell out. Saved geometry is **dropped when it no longer lands on a screen** — a laptop undocked from the monitor it was maximized on would otherwise reopen off-screen, with no title bar to drag back — and the tracker needs an explicit `flush()`, because the ordered quit ends in `app.exit`, which tears the windows down **without emitting `close`**, so a drag made a moment before ⌘Q would otherwise be the one thing a session forgot. Fullscreen is not persisted: reopening in it hides the window the user was looking for. A second window cascades off the one it was opened from, up and to the left when down and to the right would run off the screen — _not_ centred, which for an already-centred opener lands the new window exactly where cascading exists to avoid.

**Spellchecking** is session-wide, so one setting covers Content, a Board's Text Blocks and the name fields with no per-component wiring. Exactly **one** language, never a union: a second enabled dictionary makes every word _it_ knows correct too, which for a vocabulary full of invented names quietly stops the checker finding anything. The locale's own dialect first, then any dialect of the same language, then English — and sayably _none_, since `setSpellCheckerLanguages` throws on a dictionary it cannot load. Two consequences. The Entity title carried `spellcheck="false"`, which had to go: a name is prose too, and an opt-out in the markup is the one field a session-wide setting cannot reach. And Electron ships **no default context menu at all**, so a right-click in Content did nothing — meaning suggestions, the half of spellchecking that _fixes_ a word rather than underlining it, had nowhere to appear. Built as one more pure template, and it is where **Add to Dictionary** lives: a worldbuilder's invented names are the vocabulary, not the mistakes.

**Multi-window** makes "the window" plural everywhere it was singular: a menu Command now goes to the focused window, and the second-instance focus does too. New Window is main's own action rather than a Command, so — unlike every item in the "displayed, not bound" rule — it **binds its chord for real**: there is no renderer dispatcher to take it from. ⌘⇧N rather than ⌘N, leaving the more obvious chord for a future in-app "new Entity".

## Considered Options

- **Tauri instead of Electron.** Rejected on the dependency graph, not on taste: `better-sqlite3`, `sharp` and `@node-rs/argon2` are native Node modules, and Nest is a Node framework, so Tauri would need a bundled Node sidecar anyway — paying Rust _and_ keeping Node.
- **Nest in an Electron `utilityProcess`.** The better long-term shape. Main's event loop drives window management, native menus, IPC and dialogs — _and_ every HTTP response, since Nest sits there. Two things occupy it synchronously: `better-sqlite3` (every query) and, with the default `strictZipGuard: false`, fflate's `unzipSync` during vault import — which ADR-0036 measured at **~1 s for a 1200-note vault** before a single Entity is written. Reindex is the same shape across every Entity. Past ~100 ms of blocked loop the menu bar feels it; past ~1 s macOS draws the not-responding state. (`sharp` is _not_ an offender: libvips runs on libuv's threadpool, so thumbnailing can starve concurrent fs work but does not block the loop.) Deferred, but the move is **not** as free as "Nest boots and reports its port": session minting crosses the boundary too, since main currently calls `AuthService.mintSession()` directly and would instead have to ask over IPC — making `renewSession()` a renderer → main → child → back round trip — plus a second lifecycle to own (crash policy, and an ordered shutdown that revokes the session and lets Nest's hooks close the SQLite handle before main quits). Note also that a `utilityProcess` runs _Electron's_ Node, not plain Node, so it buys nothing on native-module rebuilds. **The tripwire is measured, not felt: instrument event-loop lag in main (a coarse `setInterval` probe) and see which handlers hold it.** If only import and Reindex show up, a `worker_threads` Worker with its own SQLite connection is the smaller fix — at the cost that WAL permits one writer, so main's autosave meets `SQLITE_BUSY` while the worker holds a write transaction unless a `busy_timeout` is set.
- **No socket: a custom `protocol.handle` bridging into Nest.** Architecturally the strongest — zero listening port, so the localhost surface vanishes, and `<img src="hexly://assets/...">` still resolves. Rejected for v1: it needs a bespoke Web-`Request`↔Express adapter, and it puts SSE streaming and multipart upload on unproven ground for a threat the session cookie already closes.
- **Replacing HTTP with IPC.** An Angular `HttpBackend` swap could route `HttpClient` transparently, but `EventSource` and `<img src>` don't go through `HttpClient`, so live-follow and every asset reference would need their own bridge. More forks than the whole shell.
- **Desktop as a native shell for a remote Instance**, or **local-first with sync.** Rejected: the first makes every affordance gate per-connection instead of per-install and needs a connection picker plus remote login; the second needs a change log, a per-Field conflict policy, and asset and ACL reconciliation — several times the size of the shell.
- **A user-chosen Instance Directory, or Obsidian-style switchable vaults.** Rejected on the WAL hazard above and, for vaults, on scope: N Nest instances or restart-to-switch, per-vault session minting, a recents list and a first-run flow. `assets.dir` serves the real underlying need.
- **Seeding a starter World at first run.** Rejected: `worlds.page.ts` already documents "zero Worlds shows an empty state with a Create affordance, never an auto-redirect", and `POST /api/worlds/import` mints a World from a vault — which is a new user's likely first action. A junk "Sole User's World" that everyone renames is worse than the empty state that exists.

## Consequences

- **`NODE_ENV=production` must not be set in the desktop main.** `COOKIE_OPTS.secure` keys on it (`auth.controller.ts`), and a `secure` cookie is never set over plain `http://127.0.0.1` — the same trap ADR-0008 hit for e2e, with the same resolution: run the prod _build_ without the literal env value.
- **Native modules are the packaging risk.** `better-sqlite3` needs an Electron rebuild; `sharp` ships per-platform prebuilds plus libvips and must be `asarUnpack`ed; `@node-rs/argon2` is napi-rs and ABI-stable, so it generally rides along. Each CI runner installs its own platform's binaries. Two things fell out of building it (#319): the Electron major is chosen for an **ABI `better-sqlite3` publishes a prebuild for** — otherwise every runner needs a compiler toolchain — and on macOS the rebuilt addon must be **ad-hoc re-signed**, because the code-signing monitor answers `dlopen` of the linker-signed prebuild with `SIGKILL (Code Signature Invalid)`, mid-boot, with no JS error to catch. One `node_modules` holds one ABI, so dev switches between the Node and Electron builds rather than holding both.

Packaged (#327) with electron-builder, whose **app directory is the workspace root**: dependency pruning follows the one root `package.json` this repo has, and since the desktop bundle keeps every dependency external, "the root package's production dependencies" is by construction what the app needs at runtime — including a runtime-only import like `yaml` (#326) that a hand-written app-directory dependency list would be a second place to forget. The cost is that the SPA's own dependencies ride along in the archive, which is most of a ~100 MB `app.asar`. Four things fell out. **electron-builder's own rebuild is not forced**, so `@electron/rebuild`'s `.forge-meta` marker makes it a no-op after `pnpm native:node` has swapped the binary underneath — it packaged Node's ABI against Electron's, which dies at the first query — so `npmRebuild: false` and the existing `--force` target owns the rebuild instead, and that target's ad-hoc re-signing matters _more_ here than in dev, because an unsigned build signs nothing on the way past. The **`asarUnpack` set is stated rather than inferred**: electron-builder unpacks a module containing a `.node` on its own, but the image library's binaries live in _sibling_ `@img/*` packages, which is exactly the kind of thing that is true until it isn't. The **smoke check is a Playwright launch of the artifact**, not a script beside it — the Electron suite's fixture already knows how to wait for a boot, so the package is one more `LaunchTarget` and the assertions are the list a successful build cannot vouch for: a World created, an image thumbnailed to `image/webp` (a status alone would pass, since serving falls back to the original bytes — #325), a password hashed and verified, `yaml` resolvable. `require` is not in scope inside `app.evaluate`, so those last two go through `process.mainModule.require`, which _is_ main's own resolution. And a **native-module failure reports itself misleadingly**: the `dlopen` throw is logged by Nest's exception handler while boot carries on, so the visible error is a later null `db` — which is why the fix-it hint about ABIs is attached to the launch itself.

- **The ordered quit has to drop the renderer's sockets** before closing Nest. `server.close()` waits for open connections, and a live-follow SSE stream (ADR-0044) never ends on its own — so with an Entity open, a quit that only awaited `app.close()` would hang forever. The renderer is going away with the process, so `closeAllConnections()` costs nothing here.
- **A crash quits without revoking**, and a no-expiry session is one the expiry sweep can never reap, so each launch clears the Sole User's previous sessions before minting its own. Otherwise the table grows by one unreachable-but-valid credential per unclean exit.
- **Distribution is unsigned, built by a CI matrix.** A GitHub Actions matrix over macos/windows/ubuntu runs electron-builder on release and attaches artifacts beside the existing ghcr.io image. **No auto-update**, because Squirrel.Mac will not update an unsigned bundle — the two are one decision, not two. On macOS 15+ the Finder right-click bypass is gone for unsigned apps, so installation is documented as System Settings → Privacy & Security → "Open Anyway". Signing later is an electron-builder config plus secrets.
- **`/assets/...` stays unauthenticated on loopback**, so a local process that already knows a sha256 can read those bytes. Unchanged from ADR-0034's accepted position, and it has the same file access anyway.
- **E2E gains an Electron project** (`_electron.launch()`) kept deliberately thin — the window opens, the Sole User is authenticated with no login, a second launch focuses the first window instead of booting a second server, the menu exists with ⌘K displayed-not-bound, an edit survives relaunch, an external link does not hijack the window. Everything about hidden affordances is tested more cheaply in a browser (ADR-0071). Built as `apps/desktop-e2e` (#320) with three of those — the authenticated window, the second launch, the surviving edit; the external-link fact arrives with the feature it describes — joined by the two facts of #321 that need a shell: a session deleted under the running app recovering itself on the next navigation, and a forged `Host` being rejected, which needs a raw socket because no browser will send one. The menu (#322) adds three more, read off the live `Menu` in main: ⌘K displayed with `registerAccelerator: false` while the native roles keep their chords, the chord opening the Palette through the renderer _and_ the menu item opening the same one, and the bridge's new member. The window facts (#323) add the external link handed off by both paths while our own `window.open` gets a second Hexly window, the second window on the same Instance live-reconciling an edit made in the first, and the geometry surviving the same relaunch the edit does. **Three traps for later specs**, each a place a shell behaves unlike a browser: `waitForURL` resolves before the SPA is listening, so a keydown sent in that gap is dropped — wait for something rendered first; a navigation the shell _cancels_ leaves Playwright waiting for a commit that never comes, so a hand-off is clicked with `dispatchEvent` and the window's URL is read off `webContents` in main rather than off the `Page`; and `output()` only holds what main wrote after Playwright took the process over, which is after `whenReady`, so the first lines of `boot` are a diagnostic rather than something to assert. Run with `nx e2e desktop-e2e`, deliberately outside the everyday `nx e2e web-e2e` gate: it needs the Electron-ABI `better-sqlite3`, and one `node_modules` holds one ABI, so the two suites cannot share a working tree state — let alone a CI job. A run's whole isolation is `--user-data-dir` pointed at a temp folder, since the pinned Instance Directory _and_ the single-instance lock both hang off `userData`; that also keeps a run from being answered by a real Hexly the developer has open.
