# Hexly ships as a Desktop App: Electron hosts the API in-process on loopback

Hexly has called itself a "desktop-style" app since ADR-0002, and ADR-0036 already made its boot input a _folder_. We now ship that literally: a **Desktop App** — an Electron shell whose main process boots the same Nest `AppModule` with `app.listen(0, '127.0.0.1')` and points a `BrowserWindow` at the resulting ephemeral port. ADR-0008's one-process-one-origin topology _is_ the desktop topology, unchanged: the same Nest process serves `/api`, the built SPA, and `/assets/...` capability URLs, so cookies, SSE live-follow (ADR-0044) and asset `src` attributes all keep working with no client fork. The Desktop App is **local-only** — it hosts its own Instance and can never point at a remote one; the browser already is the remote client.

## The session, and why loopback needs one

Main mints a session row for the **Sole User** at launch and writes `hexly_session` into the renderer's cookie jar (`session.cookies.set`) before `loadURL`, then revokes it on quit. `SessionAuthGuard` is untouched — it finds a genuine session — and the login page is never rendered.

Keeping a real credential is the point, not ceremony. **A loopback socket is not a security boundary**: `127.0.0.1` is not reachable from the LAN or the internet — that part is a genuine property of binding loopback rather than `0.0.0.0`, and it opens no firewall hole — but it _is_ reachable by every local process and, more importantly, by every web page the user visits, which can `fetch('http://127.0.0.1:<port>/api/...')`. The ephemeral port (`listen(0)`) means a page must scan ~16k ports to find us, which raises cost without being security.

Two walls make that acceptable, and they are load-bearing:

1. **The session cookie.** Electron's cookie jar is not the browser's jar, so an attacking page holds no token and gets a 401. "One user" never implied "no credential" — a guard that resolved the **Sole User** from an absent cookie would hand every visited web page the whole vault, which is why that option was rejected outright.
2. **The deliberate absence of CORS** (ADR-0008 adds no `enableCors()`). Even for an unauthenticated route, a cross-origin page cannot _read_ the response body.

DNS rebinding is the attack that pierces wall 2 — an attacker domain resolving to `127.0.0.1` makes the page same-origin — but it does not pierce wall 1, because the browser then sends cookies scoped to the attacker's host, not ours. In the desktop profile we additionally reject requests whose `Host`/`Origin` is not the loopback address we bound: cheap, and it closes rebinding at the door rather than relying on the cookie alone.

Two things keep this in proportion. A local process running as the user can simply read `hexly.db`, so for _that_ threat the socket adds nothing filesystem access did not already grant; the socket's only novel exposure is the browser-page path, which the two walls close. And the category is not permanent — the `protocol.handle` option below removes the listening socket entirely, and remains the upgrade if this ever stops being acceptable.

Because identity is never in question here, a 401 is recoverable rather than fatal: the renderer asks main to re-mint through the preload bridge and retries. The condition is the **bridge's presence**, not a config flag — "can I renew?" is a capability question, so it gets a capability check (ADR-0071 draws the same line for policy questions). This matters because `authGuard` otherwise routes to `/login`, which in the desktop profile is a dead end: the Sole User has no password, so any 401 — expiry, a cleared jar, a replaced DB — would strand the user permanently.

## The Instance Directory is pinned; only assets move

The Instance Directory is `app.getPath('userData')/hexly`, fixed and not user-choosable. **The pin is the safety property.** ADR-0002 runs SQLite in WAL mode, and a cloud-sync daemon or network mount rewriting `hexly.db`/`-wal` underneath an open handle is a known corruption path — so the most popular choice a folder picker would offer (`~/Dropbox/Hexly`) is precisely the one that eats worlds.

Asset bytes are content-addressed and write-once (ADR-0034), so they are safe anywhere: a partially-synced or unmounted file degrades to missing bytes, never to a corrupt vault. They are also the bulk of the data. So `assets.dir` (see the ADR-0034 amendment) is the escape hatch, with a desktop picker that moves the bytes with progress, verifies by hash, rewrites `hexly.yml` and calls `app.relaunch()` — config is read once at boot, so applying it means a restart we own. Portability of the _authored_ substance stays the Vault export (ADR-0033), which is better in a git repo or a synced folder than a `.db` could ever be.

## The native menu displays accelerators; the dispatcher owns them

An OS menu accelerator is consumed before the renderer sees the keydown, which would make the menu a second dispatcher — blind to `pushModalScope()` and to the editable-target gate, reintroducing exactly the bugs ADR-0063 was written to kill (a chord firing behind an open `<dialog>`). So menu items that duplicate in-app actions set `registerAccelerator: false`: ⌘K is _displayed_ in the menu but not bound, and the renderer's single dispatcher keeps ownership. A menu click IPCs into the renderer and invokes the **Command** — widening `Command` from a Palette entry to an invocable action with two surfaces. Genuinely native chords stay native roles (clipboard, zoom, reload, window, quit); the dispatcher never claimed those, and the clipboard roles must be registered or ⌘C stops working in web content on macOS.

Alongside: a single-instance lock (two processes running boot migrations on one SQLite file is a race, ADR-0027), external links handed to the system browser via `setWindowOpenHandler` and a `will-navigate` guard (otherwise a link inside Content navigates the SPA away with no back button), window-state persistence, Electron's built-in spellchecker (the app is fundamentally a prose tool), and multi-window — coherent precisely _because_ live-follow was kept, so two windows on one Entity reconcile through the nudge bus.

## Considered Options

- **Tauri instead of Electron.** Rejected on the dependency graph, not on taste: `better-sqlite3`, `sharp` and `@node-rs/argon2` are native Node modules, and Nest is a Node framework, so Tauri would need a bundled Node sidecar anyway — paying Rust _and_ keeping Node.
- **Nest in an Electron `utilityProcess`.** The better long-term shape. Main's event loop drives window management, native menus, IPC and dialogs — _and_ every HTTP response, since Nest sits there. Two things occupy it synchronously: `better-sqlite3` (every query) and, with the default `strictZipGuard: false`, fflate's `unzipSync` during vault import — which ADR-0036 measured at **~1 s for a 1200-note vault** before a single Entity is written. Reindex is the same shape across every Entity. Past ~100 ms of blocked loop the menu bar feels it; past ~1 s macOS draws the not-responding state. (`sharp` is _not_ an offender: libvips runs on libuv's threadpool, so thumbnailing can starve concurrent fs work but does not block the loop.) Deferred, but the move is **not** as free as "Nest boots and reports its port": session minting crosses the boundary too, since main currently calls `AuthService.mintSession()` directly and would instead have to ask over IPC — making `renewSession()` a renderer → main → child → back round trip — plus a second lifecycle to own (crash policy, and an ordered shutdown that revokes the session and lets Nest's hooks close the SQLite handle before main quits). Note also that a `utilityProcess` runs _Electron's_ Node, not plain Node, so it buys nothing on native-module rebuilds. **The tripwire is measured, not felt: instrument event-loop lag in main (a coarse `setInterval` probe) and see which handlers hold it.** If only import and Reindex show up, a `worker_threads` Worker with its own SQLite connection is the smaller fix — at the cost that WAL permits one writer, so main's autosave meets `SQLITE_BUSY` while the worker holds a write transaction unless a `busy_timeout` is set.
- **No socket: a custom `protocol.handle` bridging into Nest.** Architecturally the strongest — zero listening port, so the localhost surface vanishes, and `<img src="hexly://assets/...">` still resolves. Rejected for v1: it needs a bespoke Web-`Request`↔Express adapter, and it puts SSE streaming and multipart upload on unproven ground for a threat the session cookie already closes.
- **Replacing HTTP with IPC.** An Angular `HttpBackend` swap could route `HttpClient` transparently, but `EventSource` and `<img src>` don't go through `HttpClient`, so live-follow and every asset reference would need their own bridge. More forks than the whole shell.
- **Desktop as a native shell for a remote Instance**, or **local-first with sync.** Rejected: the first makes every affordance gate per-connection instead of per-install and needs a connection picker plus remote login; the second needs a change log, a per-Field conflict policy, and asset and ACL reconciliation — several times the size of the shell.
- **A user-chosen Instance Directory, or Obsidian-style switchable vaults.** Rejected on the WAL hazard above and, for vaults, on scope: N Nest instances or restart-to-switch, per-vault session minting, a recents list and a first-run flow. `assets.dir` serves the real underlying need.
- **Seeding a starter World at first run.** Rejected: `worlds.page.ts` already documents "zero Worlds shows an empty state with a Create affordance, never an auto-redirect", and `POST /api/worlds/import` mints a World from a vault — which is a new user's likely first action. A junk "Sole User's World" that everyone renames is worse than the empty state that exists.

## Consequences

- **`NODE_ENV=production` must not be set in the desktop main.** `COOKIE_OPTS.secure` keys on it (`auth.controller.ts`), and a `secure` cookie is never set over plain `http://127.0.0.1` — the same trap ADR-0008 hit for e2e, with the same resolution: run the prod _build_ without the literal env value.
- **Native modules are the packaging risk.** `better-sqlite3` needs an Electron rebuild; `sharp` ships per-platform prebuilds plus libvips and must be `asarUnpack`ed; `@node-rs/argon2` is napi-rs and ABI-stable, so it generally rides along. Each CI runner installs its own platform's binaries. Two things fell out of building it (#319): the Electron major is chosen for an **ABI `better-sqlite3` publishes a prebuild for** — otherwise every runner needs a compiler toolchain — and on macOS the rebuilt addon must be **ad-hoc re-signed**, because the code-signing monitor answers `dlopen` of the linker-signed prebuild with `SIGKILL (Code Signature Invalid)`, mid-boot, with no JS error to catch. One `node_modules` holds one ABI, so dev switches between the Node and Electron builds rather than holding both.
- **The ordered quit has to drop the renderer's sockets** before closing Nest. `server.close()` waits for open connections, and a live-follow SSE stream (ADR-0044) never ends on its own — so with an Entity open, a quit that only awaited `app.close()` would hang forever. The renderer is going away with the process, so `closeAllConnections()` costs nothing here.
- **A crash quits without revoking**, and a no-expiry session is one the expiry sweep can never reap, so each launch clears the Sole User's previous sessions before minting its own. Otherwise the table grows by one unreachable-but-valid credential per unclean exit.
- **Distribution is unsigned, built by a CI matrix.** A GitHub Actions matrix over macos/windows/ubuntu runs electron-builder on release and attaches artifacts beside the existing ghcr.io image. **No auto-update**, because Squirrel.Mac will not update an unsigned bundle — the two are one decision, not two. On macOS 15+ the Finder right-click bypass is gone for unsigned apps, so installation is documented as System Settings → Privacy & Security → "Open Anyway". Signing later is an electron-builder config plus secrets.
- **`/assets/...` stays unauthenticated on loopback**, so a local process that already knows a sha256 can read those bytes. Unchanged from ADR-0034's accepted position, and it has the same file access anyway.
- **E2E gains an Electron project** (`_electron.launch()`) kept deliberately thin — the window opens, the Sole User is authenticated with no login, the menu exists with ⌘K displayed-not-bound, an edit survives relaunch, an external link does not hijack the window. Everything about hidden affordances is tested more cheaply in a browser (ADR-0071).
