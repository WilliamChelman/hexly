# Each lib owns its translations, as a Transloco scope

ADR-0014 put every user-facing string in **one catalog per language**, owned by `web-core` (`en.json`, `fr.json`, copied to `assets/i18n/`), and explicitly rejected per-feature scopes: at that string count, the only payoff of scopes — shaving KB off the initial transfer — was negligible against the per-folder `provideTranslocoScope` tax.

That was right about the bytes and wrong about the ownership. The catalog grew to 568 keys, and `web-core` — a lib that renders almost nothing — became the place every other lib's copy lived. A lib was not self-contained: changing web-map meant editing web-core, a plugin could not ship its own words, and nothing stopped two features from colonizing the same namespace (`editorShell.*` ended up half web-map's tool palette and half the app's entity-page chrome; `noteView.*` likewise split between content-editor and the app).

So this ADR supersedes two bullets of ADR-0014 — "one global file per language" and copy owned by `web-core` — and keeps everything else it decided (runtime switching, Transloco, semantic keys, English as source and fallback, the client owning all copy, an unlocalized server).

## What we decided

- **One catalog per project, declared by the project that renders it.** Each lib carries `src/i18n/catalogs/{en,fr}.json` and a `TranslationScope` naming its Transloco **scope**: `ui` (web-ui), `map` (web-map), `editor` (content-editor), `fields` (web-entity), `dnd` (the bundled plugin), `core` (web-core's own service toasts). The app keeps the **root** catalog — its pages and shell, 386 keys — still served from `assets/i18n/` by the HTTP loader. `web-core` is left holding the i18n _plumbing_ (config, loader, the drift comparator, the testing harness) and one string of its own.

- **The scope name is the key prefix.** Transloco flattens a loaded scope into the active language's translation object under its scope name, so a catalog `{ toolPalette: { select: 'Select' } }` declared under scope `map` answers `map.toolPalette.select`. Ownership is legible at the call site, and a lib's keys cannot collide with another's by construction. This is what forced `editorShell.*` and `noteView.*` apart into the halves that were always two things.

- **One namespace, one owner — enforced.** Because scopes share a single flat key space with the root catalog, a scope named `map` and a root `map.*` namespace would answer the same key, with load order deciding the winner. The `web:i18n-sync` gate now walks every catalog, checks en↔fr parity **per catalog**, and fails if two projects claim the same prefix. That is what makes single ownership a rule rather than an aspiration.

- **Eager by default; lazy only where the injector tree contains every reader.** Transloco loads a scope when a pipe or directive that can _see_ its provider renders. That is too late for copy read imperatively (`TranslocoService.translate` — route titles, toasts) or carried **as data** across libs (a plugin's `TypeDefinition.labels` are translation keys, resolved by the app's command palette and entity header, where the plugin has no pipe of its own). Such a reader gets a raw key — and `TranslocoPipe` **memoizes that miss**, so it stays wrong even after the scope lands. So `ui`, `editor`, `fields`, `dnd` and `core` are registered by the app with `provideEagerTranslations(...)`, and `LocaleService` loads them alongside the root catalog before the first paint and on every language switch. Only **`map`** is lazy: the app mounts just `MapView`, every `map.*` reader lives in its template subtree, and so web-map provides that scope itself and its 74 keys are fetched only when a hex map is on screen.

- **A lib's catalogs are reachable without its code.** Each lib exposes a `@hexly/<lib>/i18n` entry point holding only the scope declaration and its dynamic `import()` loaders. Registering a scope must not drag the lib in: importing content-editor's translations through its main barrel pulled **Tiptap** out of the lazy entity chunk and into first paint (+468 KB, over the bundle budget) to register a few kilobytes of copy.

- **Specs compose the catalogs they render.** `provideTranslocoTesting(...catalogs)` is now variadic and each project exports its real catalogs from `@hexly/<lib>/testing`, keyed by load path (`'map/en'`). A lib's specs load its own copy; the app's harness composes all of them, since a page can mount a component from most of the libs. Assertions still read against real English copy, so they keep doubling as proof that the keys resolve.

## Considered options

- **Keep the single catalog, split only the files at build time** (merge per-lib fragments into one `en.json`). Rejected: it fixes where strings _sit_ without fixing who _owns_ them — nothing enforces one owner per namespace, and a plugin still cannot ship words without a build step reaching into its files.
- **Contributed catalogs merged in memory** (each lib exports `{en, fr}`, a custom loader deep-merges them). Simpler, and it keeps today's keys unchanged — but it puts every language of every lib in the JS bundle, has no lazy story at all, and re-implements a merge that Transloco already does properly with scopes.
- **A scope per existing namespace** (scope `owners`, scope `editorShell`, …), which would have left every call site untouched. Rejected: it perpetuates exactly the ambiguity we are removing — `editorShell` is two owners' copy wearing one name — and multiplies loaders per lib.

## Consequences

- **~180 call sites moved to prefixed keys** (`editorShell.toolPalette.*` → `map.toolPalette.*`, `owners.*` → `ui.owners.*`, `plugins.dnd.*` → `dnd.*`, …). Mechanical, and the specs — which assert real copy — are what proved it.
- **Two strings are deliberately duplicated across catalogs**, because a lib may not read another project's copy: `map.canvas.label` alongside the app's `editorShell.hexMap` ("Hex map"), and `map.untitledNote`/`map.untitledMap` alongside the app's `domain.untitled*`. The second pair is a seam, not a happy accident: web-map's inspector creates an entity and needs the type's _untitled_ label, but the `TypeRegistry` that owns those labels lives in `apps/web`, so the lib cannot ask it. When the registry moves to `web-entity`, web-map should resolve the label through it and the duplicates collapse. The drift gate cannot catch these — only review can.
- **An eager scope is _loaded_, never _provided_.** `provideEagerTranslations` deliberately does not register `TRANSLOCO_SCOPE`. Transloco's own `provideTranslocoScope` exists to make a pipe _trigger_ a scope's load, which an eager scope does not need — and registering it at the root put every lib's scope into every component's injector, where **`translateSignal` reads `TRANSLOCO_SCOPE` and prefixes the key with it** (the pipe and `TranslocoService.translate` never do). The app's `translateSignal('entityTags.addPlaceholder')` duly resolved `dnd.entityTags.addPlaceholder` and rendered that raw key into the tags editor. Worth dwelling on how it hid: **no TestBed could catch it**, because the testing harness registers catalogs, not scopes — only the real `app.config` had the providers. The regression test in `translation-scope.spec.ts` now reproduces `app.config`'s wiring, and an e2e asserts the placeholder's real copy.
- **A lib that provides its own scope inherits the prefixing.** Inside `MapView`'s subtree the scope _is_ in the injector, so a `translateSignal` there would resolve `map.foo` from `'foo'`. web-map uses the pipe throughout; a lib reaching for the signal API must pass scope-relative keys and know the two APIs read differently.
- **Bootstrap fetches a few small chunks instead of one file**: the root catalog over HTTP, plus one dynamic-import chunk per eager scope. They are 1–4 KB each and load in parallel, and `map`'s 74 keys now never reach a user who opens no map.
- **A plugin ships its own translated copy**, which is the point: `libs/plugin-dnd` declares scope `dnd`, and its `TypeDefinition.labels` keys resolve because the app registers that scope eagerly — the same path any future bundled plugin takes.
- **No `CONTEXT.md` change.** The domain vocabulary is untouched; this moves where words live, not what they mean.

## Amendment (2026-07, #199): `map` joins the eager scopes, and a switch re-announces the language

The Hex Map's web half became one `providePluginHexmap()` (ADR-0050, #199), which carries the type's chrome — its header eyebrow, its create heading, its untitled default. Those are `TypeDefinition.labels`, and labels are **translation keys read as data by the app**: the entity header, the entity browser, and the command palette render them where the plugin has no pipe of its own. That is the exact condition this ADR gives for an eager scope, so `map` is now registered by `providePluginHexmap()` like `dnd`'s, and `MapView` no longer provides it. **No scope is lazy any more**, and the "only `map` is lazy" rule above is retired: a plugin's scope rides its provider, and the app's `provideEagerTranslations(...)` names only the libs it composes directly.

The `map.untitledNote` / `map.untitledMap` duplicates are **gone**, which this ADR predicted would happen "when the registry moves to `web-entity`". The registry did not move; its _read contract_ did. `ENTITY_TYPES` (a token in `web-entity`, bound to the app's `TypeRegistry`) lets any lib ask a type for its name and chrome, so the Entity-Link picker — now `web-entity`'s, no longer the map's — resolves a created Entity's untitled label through the registry instead of carrying its own copy of two strings. `map.canvas.label` still duplicates the chrome's "Hex map": that one is the canvas's own accessible name, and both now live in this plugin's catalog anyway.

Making `map` eager exposed a **latent race in a language switch**, which the map's e2e caught and every eager scope had:

- A `TranslocoPipe` carrying no scope of its own re-resolves the moment the **root** catalog lands, and nothing re-emits when a scope lands after it. `LocaleService.set()` loaded the root and the eager scopes in parallel, so the loser of that race rendered raw keys — permanently, since the pipe memoizes. It never surfaced because the one scope whose copy a user watches during a switch was the lazy one, and a lazy scope's pipes reload it themselves.
- The repair is one line: `set()` **re-announces the language** once every catalog has landed. `langChanges$` is deliberately not deduplicated (Transloco's own comment says so), so re-setting the same language re-emits and every pipe re-resolves — with the scopes now in hand. `locale.service.spec.ts` pins it with a scope that resolves _after_ the root catalog.
